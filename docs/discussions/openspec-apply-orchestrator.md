# Назначение и принципы оркестратора OpenSpec Apply

## Цель обсуждения

Определить, какую работу пользователь хочет передать CLI в этом репозитории, какое участие сохранить за собой и при каких условиях процесс сможет восстанавливаться после прерываний. Граница обсуждения — назначение продукта, желаемый процесс и ограничения, определяющие его осуществимость. Детальное проектирование интеграций, спецификации и план реализации пока не создаются.

## Текущее понимание

Репозиторий предназначен для CLI, который ведёт выбранный OpenSpec change через пользовательский процесс Apply: проверяет рабочую среду, организует коммиты, разбирает замечания ревью, планирует задачи очередной фазы, запускает обсуждение каждой задачи, её выполнение и проверку. Основные внешние инструменты — Git, OpenSpec и Paseo. Для одного change создаётся один workspace Paseo, который переиспользуется при продолжении работы; сессии разных задач создаются отдельно внутри него. Workflow не зависит от конкретной схемы change. CLI разбирает заголовки фаз плана, получает из OpenSpec CLI номера задач, их названия и отметки выполнения, а из файлов ревью извлекает открытые проблемы для обсуждения. Номера задач не подменяются внутренними ID OpenSpec. В пограничных случаях CLI также проверяет незакоммиченные изменения и неотслеживаемые файлы Git.

Рабочая гипотеза о ценности инструмента: освободить пользователя от постоянного определения очередного действия, запуска подходящего скилла и переноса контекста между сессиями, сохранив его решения по замечаниям и разрешение на выполнение каждой задачи. Это формулировка намерения для дальнейшего уточнения, а не утверждённая спецификация.

Связь задач с фазами определяется общим правилом нумерации: первая часть номера задачи обозначает фазу. Например, `2.3` относится к фазе 2. Пользователь подтвердил это соглашение для workflow независимо от конкретной схемы change.

Разделение ответственности подтверждено пользователем: CLI управляет процессом по явным правилам, выдаёт поручения, запрашивает ответы в определённом формате и сверяет их с доступными фактами Git, OpenSpec и Paseo. Содержательные решения и оценки выполняют агенты в рабочих сессиях и ревью. Отдельная рассуждающая модель внутри CLI не требуется. Конкретные форматы ответов и проверки для каждого действия ещё предстоит определить.

Параметры запуска агентов задаются по типам сессий в конфигурационном файле репозитория, из которого запускается CLI. Пользователь может указать провайдера, точную модель, уровень reasoning, при необходимости профиль и другие поддерживаемые параметры. Эти значения не зашиваются в программу. Первоначальные промпты и технические запросы поставляются с CLI и изменяются вместе с его версиями. Промпты общие для проектов и, по ожиданию пользователя, меняются редко, поэтому их дублирование в проектных конфигурациях не оправдано. Конфигурация задаёт параметры агентов и не служит журналом прогресса. Точный механизм получения итогового ответа ещё не выбран.

CLI заканчивает работу, когда выполнена последняя фаза плана, больше нет задач для выполнения или фаз для планирования, последняя задача прошла ревью и не осталось открытых замечаний для разбора и появления новой работы. Эти условия проверяются совместно по актуальному состоянию. Архивирование change выполняет сам пользователь; оно не входит в работу CLI.

Желаемая основа — повторяющийся цикл: прочитать актуальное состояние, выбрать одно допустимое действие, сопровождать его и заново прочитать состояние. Все источники — заголовки плана, список задач OpenSpec CLI, открытые проблемы из ревью, Git и workspace и агенты Paseo — перечитываются на протяжении всей работы. Чтение не ограничивается запуском процесса или первоначальным построением очереди. CLI продолжает наблюдать состояние и во время ожидания своих сессий или участия пользователя, сохраняя последовательность собственных действий. Процесс должен быть долгоживущим и устойчивым к прерыванию, без зависимости от сохранившейся памяти своего процесса.

Каждый шаг оркестратора должен логироваться и выводиться в `stdout` по ходу работы, чтобы пользователь мог проследить, чем CLI занимался и чем занимается сейчас, включая ожидание агента или человека. Этот вывод служит наблюдению и диагностике; восстановление по-прежнему опирается на Paseo и обычные результаты workflow. Подробность понятия «каждый шаг», формат сообщений и способ сохранения вывода для последующего просмотра ещё предстоит определить.

Допустимые источники состояния выполнения — существующие workspace и агенты Paseo, а также файловая система после обычного рабочего процесса. Собственные отметки прогресса в репозитории запрещены, в том числе при записи через агентов. При этом пользователь явно разрешил конфигурационный файл с параметрами запуска по типам сессий; настройки не являются состоянием выполнения. Рабочее видение восстановления — найти ранее созданный workspace, распознать соответствующие сессии и определить уже проведённые и незавершённые действия по их состоянию. История разговора в Paseo может содержать результат обсуждения без записи в `tasks.md`; достаточность и сохранность этих данных ещё предстоит проверить.

В том же workspace пользователь может создавать собственные сессии вперемешку с сессиями оркестратора. CLI должен различать их; формат `title` предложен как возможный способ, но окончательный механизм не выбран. Последовательность относится исключительно к агентам, созданным оркестратором, включая автономные сессии и сессии с участием человека. Собственные сессии пользователя не входят в этот процесс: их наличие, активность и закрытие не влияют на выбор действий или ожидание CLI. Последовательность обусловлена зависимостями между обсуждением, выполнением и ревью задач; искать возможности параллелизма не требуется. В управляемом процессе пользователь вручную закрывает только сессии, требующие его активного внимания. Автономные сессии оркестратор закрывает сам, убедившись в полном выполнении поручения. Закрытие своей сессии служит сигналом заново оценить состояние. Для соответствующей сессии ревью закрытие означает, что это ревью проведено; найденные проблемы CLI получает из актуальных файлов ревью. Для обсуждения задачи по-прежнему требуется определить человеческое решение по его итогам.

CLI отправляет уведомление каждый раз, когда требуется вмешательство пользователя. Для заранее предусмотренного обсуждения он сначала дожидается завершения первоначальной работы агента, затем уведомляет о готовности к взаимодействию со ссылкой на соответствующую сессию Paseo. Если автономная работа пошла не по плану и требуется человек, уведомление отправляется при возникновении этой потребности. Выбранный на данный момент канал — HTTP-запрос к ntfy; в дальнейшем возможен аналогичный сервис. Сам запуск агента ещё не является поводом для уведомления о готовности. Если после перезапуска результат предыдущей отправки неизвестен и участие человека всё ещё требуется, CLI отправляет уведомление повторно; пользователь согласовал возможный дубль в этом случае.

Первичная проверка установленного Paseo 0.7.2 подтверждает наличие команд поиска агентов, включая архивированных, чтения истории и получения признака архивирования. Это поддерживает выбранное направление, но ещё не доказывает весь протокол восстановления. Основные открытые вопросы теперь — распознавание своих сессий и предмета их работы, восстановление результата после прерывания и его применимость к текущим артефактам, а также предотвращение повторного запуска собственного действия.

## Подтверждённые намерения и ограничения

- **Работа с указанным change без привязки к схеме.** Пользователь запускает CLI для конкретного change. Управление workflow опирается на файлы ревью, план и задачи; наличие именно схемы `intent-driven` или её полного графа артефактов не является условием совместимости. Агенты следуют правилам выбранного change и читают нужный им контекст. Планирование задач последующих фаз входит в работу CLI; правила обнаружения файлов и допустимого отсутствия ещё не созданных задач или ревью нужно уточнить.
- **Фазы из заголовков плана.** CLI получает последовательность фаз, разбирая соответствующие заголовки файла плана. Содержательная интерпретация целей и требований фазы остаётся у агентов.
- **Номер задачи определяет фазу.** Первая часть номера задачи всегда обозначает номер фазы: `N.X` относится к фазе `N`. Это общее соглашение поддерживаемого workflow, а не особенность только схемы `intent-driven`. Номера из списка задач позволяют сопоставлять задачи с заголовками фаз.
- **Список задач через OpenSpec CLI.** Получать номера задач, названия без подробностей и отметки выполнения через OpenSpec CLI. Для поручений использовать именно номера задач, которыми оперирует пользователь, а не внутренние ID OpenSpec. Полный контракт задачи и её контекст агент читает в исходных артефактах; краткий список от CLI не заменяет это чтение.
- **Открытые проблемы из файлов ревью.** CLI разбирает отчёты и извлекает открытые проблемы, необходимые для обсуждения. Отчёт-источник позволяет выбрать соответствующий workflow разбора. Принятые человеком остаточные риски не считаются открытыми проблемами.
- **Git как постоянно перечитываемый источник.** Проверять наличие незакоммиченных изменений и неотслеживаемых файлов в ходе всего процесса, как и остальные входные данные. Эти сведения используются в пограничных случаях для решений о коммитах и продолжении после прерываний; они не заменяют состояние задач, ревью или сессий Paseo.
- **Три основные интеграции:** Git, OpenSpec, Paseo. Все рабочие агентские сессии запускаются через Paseo и доступны пользователю интерактивно, включая сессии без ожидаемого участия человека.
- **CLI управляет по правилам; агенты выполняют содержательную работу.** CLI выбирает действие, выдаёт поручение, запрашивает итог в определённом формате, сверяет наблюдаемые результаты и определяет переход. Интерпретация требований, реализация и содержательная оценка качества принадлежат агентам. Отдельная модель для рассуждений внутри CLI не нужна; наличие артефакта или отметки само по себе не доказывает качество работы и не заменяет ревью.
- **Настройки запуска по типам сессий в рабочем репозитории.** Для каждой запускаемой сессии CLI определяет её тип и читает соответствующие параметры из конфигурационного файла репозитория, из которого запущен. Настраиваются провайдер, точная модель, reasoning, при необходимости профиль и другие поддерживаемые параметры запуска. Название файла, формат и точные поля ещё не выбраны. Значения моделей и провайдеров не зашиваются в CLI; проектная конфигурация не содержит промптов.
- **Промпты поставляются и версионируются вместе с CLI.** Для каждого типа сессии первоначальное поручение, включая нужные рабочие инструкции и указание скилла, входит в поставку CLI. Технические запросы также принадлежат CLI. Обновление общих редко меняющихся промптов выпускается новой версией программы; копирование шаблонов между проектами исключено. При запуске CLI подставляет актуальный предмет работы — например, выбранный change и номер задачи; публичный механизм проектных шаблонов не нужен.
- **Один workspace на change.** Оркестратор создаёт workspace для выбранного change, размещает в нём рабочие сессии и переиспользует его при продолжении. Для разных задач нужны разные сессии; один разговор не используется как исполнитель всех задач change.
- **Смешанное происхождение сессий.** Внутри этого workspace пользователь может вручную создавать сессии наряду с сессиями CLI. Собственные сессии пользователя исключены из управления процессом: CLI не ждёт их, не использует их результаты как завершение своих шагов и не реагирует на их закрытие. Принадлежность к workspace сама по себе не означает принадлежность оркестратору. Пользователь предложил различать происхождение по формату `title`; это пока вариант, а не установленный формат.
- **Последовательное выполнение собственных действий.** Одновременно работает один агент, созданный оркестратором. Ограничение одинаково относится к автономным сессиям и сессиям, созданным для участия человека. Собственные сессии пользователя при проверке занятости не учитываются. Обсуждение предшествует выполнению, выполнение — ревью, а следующие задачи обычно зависят от предыдущих; параллелизм не является целью. Замечания разбираются отдельными последовательными сессиями. Точное применение правила к родительским агентам и внутренним субагентам скиллов ещё предстоит определить без параллельного выполнения зависимых шагов.
- **Ограниченное обязательное участие человека.** Обычные точки участия — разбор замечаний после предварительной работы агента и обсуждение задачи с разрешением перед выполнением. Если автоматическая сессия не справилась, CLI также привлекает пользователя.
- **Сопровождение автоматических сессий.** Оркестратор сам взаимодействует с агентом и проверяет полное завершение поручения. Принят общий принцип: итог в определённом формате сверяется с доступными фактами; конкретный протокол и проверки ещё не выбраны. После подтверждённого успеха CLI сам закрывает сессию. Если агент сообщает, что поручение не выполнено, CLI уведомляет пользователя и передаёт ему текущую сессию для разбора, сохраняя ожидание этого шага.
- **Ручное закрытие в точках участия человека.** В управляемом процессе пользователь должен закрывать только сессии, которым требуется его активное внимание: обсуждение задачи, разбор замечания или переданная ему проблема автономного выполнения. Закрытие — сигнал прочитать результат и заново выбрать действие. Автономный успешный шаг не требует ручного закрытия вкладки.
- **Уведомление после первоначальной работы агента.** Для сессии, созданной с ожиданием участия пользователя, CLI отслеживает выполнение первоначального запроса. Когда агент закончил эту работу и готов к взаимодействию, CLI уведомляет пользователя. Это относится и к обсуждению задачи, и к разбору замечания. Уведомление не отправляется лишь по факту создания сессии или запуска агента.
- **Уведомление при любой необходимости вмешательства.** Запланированное обсуждение и проблема автономного выполнения одинаково требуют уведомления. Если автономная сессия столкнулась с затруднением, требующим человека, CLI уведомляет пользователя и передаёт ему текущую сессию. Для такого случая не нужно ждать успешного завершения первоначального поручения.
- **HTTP-уведомления через ntfy со ссылкой на сессию.** На данный момент выбран ntfy; допускается аналогичный сервис в дальнейшем. CLI отправляет HTTP-запрос с сообщением о готовности и ссылкой, по которой пользователь открывает соответствующую сессию Paseo. Уведомление приглашает к взаимодействию; ожидание результата и закрытия сессии пользователем продолжается по обычным правилам.
- **Повторная отправка при неопределённости после перезапуска.** Если сервис мог принять уведомление, но CLI прервался до получения ответа, при восстановлении нужно снова проверить необходимость вмешательства. Если она сохраняется, а результат предыдущей отправки неизвестен, уведомление отправляется повторно. Возможный дубль в таком случае явно принят пользователем. Это не означает повторение уведомления на каждом проходе обычного цикла наблюдения.
- **Планирование по фазам.** Подробные атомарные задачи с собственными критериями приёмки создаются только для текущей фазы. После завершения фазы следующий пакет планируется и проходит ревью автоматически.
- **Конец работы по исчерпанию всего цикла.** CLI завершает работу только при совместном выполнении условий: последняя фаза реализована, нет невыполненных задач, нет оставшихся фаз для планирования, последняя задача прошла ревью и нет открытых замечаний, требующих разбора и способных породить новую работу. Пустой список задач текущего пакета сам по себе не означает завершение.
- **Архивирование принадлежит пользователю.** CLI не архивирует change. Отдельный обязательный финальный этап верификации сверх проверок задач и ревью не принят: пользователь определил завершение через исчерпание описанного рабочего цикла.
- **Постоянное перечитывание всех источников.** На очередных проходах цикла CLI заново читает план, список задач через OpenSpec CLI, открытые проблемы из ревью, Git и состояние Paseo. Это продолжается во время всей работы, включая ожидание своего агента или человека. После каждого действия выбор следующего шага опирается на свежие данные. Частота опроса или механизм наблюдения пока не выбраны.
- **Закрытая сессия ревью означает проведённое ревью.** Найдя собственную сессию, посвящённую соответствующему ревью фазы или задачи, CLI считает ревью проведённым, если сессия закрыта. Затем проверяет актуальные файлы ревью и направляет открытые проблемы на разбор. Отдельная запись о проведении ревью в репозитории не требуется. Автономную сессию CLI закрывает после подтверждения выполнения её поручения; при восстановлении использует сохранившийся факт закрытия.
- **Устойчивость к остановке.** Перезапуск должен продолжать работу с достигнутого состояния. Допустимы только существующие workspace и агенты Paseo и обычные результаты рабочего процесса в файловой системе; внутреннее состояние процесса не может быть необходимым источником продолжения.
- **Каждый шаг виден в логах и `stdout`.** Вывод появляется по ходу работы и позволяет проследить предыдущие действия и понять текущее действие или ожидание. Требование относится к наблюдаемости работы оркестратора; точная детализация сообщений ещё не согласована.
- **Без собственного журнала прогресса для восстановления.** Нельзя создавать собственные записи состояния выполнения в репозитории или дописывать служебные поля прогресса в существующие артефакты только ради CLI. Поручение такой записи агенту не делает её допустимой. Обычные результаты планирования, реализации, ревью и коммитов остаются допустимыми источниками. Разрешённый пользователем конфигурационный файл хранит настройки запуска; в него нельзя переносить состояние шагов или сессий. Диагностические логи и вывод в `stdout` допустимы и требуются для наблюдения, но не используются CLI как источник состояния для продолжения работы.
- **Изменения рабочего репозитория через агентов.** Сам CLI наблюдает состояние и управляет взаимодействием; изменения файлов и коммиты поручаются агентам. Обслуживание этого документа в текущем обсуждении не является поведением разрабатываемого CLI.
- **Стоимость учитывается в конфигурации.** Для коммитов пользователь хочет дешёвую модель, которая надёжно справляется с работой, и задаёт её для соответствующего типа сессии. CLI использует указанные параметры; встроенный подбор модели по цене не требуется.

## Типы создаваемых сессий

Из описанного процесса выделены восемь типов, для которых нужны отдельные настройки запуска агентов в проектной конфигурации и первоначальные промпты в поставке CLI. Это классификация поручений для обсуждения; точные ключи конфигурационного файла ещё не выбраны.

| Тип сессии | Поручение | Обычное участие пользователя |
|---|---|---|
| Подготовка коммитов | Закоммитить текущие изменения по правилам репозитория | Автономно |
| Планирование задач фазы | Сформировать задачи выбранной фазы | Автономно |
| Ревью артефактов и задач фазы | Выполнить ревью change с текущим пакетом задач | Автономно |
| Разбор замечания к артефактам | Подготовить и обсудить одно открытое замечание из `review.md` | После первоначальной работы агента |
| Обсуждение задачи | Объяснить конкретную задачу и получить решение пользователя | После первоначальной работы агента |
| Выполнение задачи | Выполнить одну согласованную задачу | Автономно |
| Ревью реализации задачи | Проверить результат выполненной задачи | Автономно |
| Разбор замечания к реализации | Подготовить и обсудить одно открытое замечание из `implementation-review.md` | После первоначальной работы агента |

Первое и последующие планирования используют один тип; конкретная фаза передаётся в поручении. Аналогично номер задачи или замечания меняет предмет сессии, но не создаёт новый тип. Классификация не добавляет действий в согласованный workflow.

При затруднении автономная сессия передаётся пользователю с уведомлением. Это смена потребности в участии человека внутри существующей сессии; отдельный тип или новый агент только ради такой передачи не нужен.

## Желаемый ход работы

Это описание поведения из обсуждения, а не план реализации или окончательная таблица приоритетов.

1. Проверить доступность необходимой среды, корректность Git-репозитория и существование выбранного change. При невозможности продолжить выдать объясняющую ошибку.
2. Найти или создать workspace change и выделить среди существующих сессий только созданные оркестратором. Дождаться своего работающего агента либо продолжить сопровождение текущего шага, если он ждёт пользователя. Собственные сессии пользователя не влияют на это решение. Перед новым поручением заново прочитать состояние. При наличии незакоммиченных или неотслеживаемых файлов запустить агента для подготовки коммитов; обработка частичной работы после сбоя остаётся открытым вопросом.
3. Сначала разбирать открытые замечания к артефактам, затем замечания к реализации. Для каждого замечания агент предварительно изучает проблему. После завершения этой первоначальной работы CLI отправляет через ntfy уведомление о готовности к обсуждению со ссылкой на сессию и ждёт, пока пользователь завершит разбор и закроет её. После этого CLI читает результат и актуальные артефакты.
4. Определить текущую фазу. Если её задачи ещё не сформированы, запустить планирование. Перед выполнением первой задачи пакета провести ревью задач и снова проверить замечания.
5. Для очередной задачи запустить обсуждение её назначения и предполагаемой реализации. Дождаться, пока агент завершит первоначальную подготовку и объяснение, затем отправить через ntfy уведомление о готовности со ссылкой на сессию. Пользователь закрывает сессию после обсуждения; CLI оценивает результат. При разрешении на выполнение запустить отдельную сессию Apply, затем ревью результата. Автономные сессии CLI закрывает сам после подтверждения полного выполнения их поручений. Перед следующей задачей вернуться к проверке замечаний.
6. После завершения пакета и подтверждения готовности фазы определить, есть ли следующая фаза. Если есть, сформировать её задачи, провести ревью и продолжить цикл.
7. Если реализована последняя фаза, нет невыполненных задач и оставшихся фаз, последняя задача прошла ревью и открытых замечаний не осталось, завершить работу CLI. Архивирование остаётся пользователю.

Чтение всех источников продолжается на протяжении всего процесса, в том числе при ожидании. Завершение действия требует нового выбора по свежему состоянию. Закрытая соответствующая сессия ревью служит свидетельством, что ревью проведено. После этого, включая самое последнее ревью, CLI читает актуальные замечания и проверяет оставшуюся работу: найденная проблема может привести к новым задачам или изменению плана. Ошибка или потребность в человеческом решении должна быть различима с успешным завершением. Точный способ различения пока открыт.

## Существующие правила и примеры в репозитории

На момент начала обсуждения в репозитории есть конфигурация инструментов, скиллы и схема OpenSpec; прикладного кода CLI, активных change и доменного глоссария не обнаружено. Каталог обсуждений создан в рамках явно вызванного навыка `discussion`.

Сведения о схеме `intent-driven` ниже описывают существующий пример пользовательского процесса. Её название, граф артефактов и особенности формата не становятся автоматически обязательными требованиями будущего CLI. Независимость от схемы и нужный набор данных подтверждены: заголовки фаз, номера и названия задач с отметками выполнения, открытые проблемы из ревью. Точные правила извлечения этих данных ещё предстоит проверить на обычных артефактах и выводе OpenSpec CLI.

- [Схема `intent-driven`, версия 5](../../openspec/schemas/intent-driven/schema.yaml) задаёт цепочку `proposal → specs → design → adr → plan → tasks`. План содержит последовательные фазы `Phase N`, а `tasks.md` — непрерывную последовательность пакетов от первой до последней представленной фазы. Незавершённые задачи допустимы только в последнем пакете.
- [Шаблон плана](../../openspec/schemas/intent-driven/templates/plan.md) отделяет направление работы и ожидаемые результаты фаз от прогресса. [Шаблон задач](../../openspec/schemas/intent-driven/templates/tasks.md) требует критериев приёмки, проверки, зависимостей, предполагаемых файлов и оценки объёма. Последняя задача пакета подтверждает условие `Ready to advance` фазы. Одного отсутствия незакрытых задач без проверки структуры фаз недостаточно для вывода о завершении change.
- Схема требует сохранять завершённые блоки задач и заголовки завершённых фаз. Исправления добавляются новыми задачами; закрытые задачи не открываются заново. Это существенно для возврата к работе после замечаний реализации.
- [OpenSpec Review Change](../../.agents/skills/openspec-review-change/SKILL.md) ведёт `review.md`. [OpenSpec Review Implementation](../../.agents/skills/openspec-review-implementation/SKILL.md) ведёт `implementation-review.md`. Эти файлы находятся в корне change, но не входят в граф артефактов схемы.
- [Формат ревью артефактов](../../.agents/skills/openspec-review-change/references/review-format.md) различает активные замечания `F<n>`, принятые человеком остаточные риски `AR<n>` и неполное ревью. Отсутствие активных замечаний не означает, что ревью было проведено полностью или что человек разрешил Apply.
- [Формат ревью реализации](../../.agents/skills/openspec-review-implementation/references/review-format.md) сохраняет диапазон проверенных коммитов и полноту проходов. Замечание может быть закрыто после согласованной передачи исправления в артефакты и конкретные отслеживаемые задачи; это не всегда означает, что код уже исправлен. Цикл должен видеть оставшуюся работу в задачах.
- Ревью реализации проверяет закоммиченный диапазон до `HEAD`; по умолчанию нижней границей служит настроенный upstream. Для проверки результата ровно одной задачи нужно определить границу её изменения. Коммиты самого `implementation-review.md` исключаются из цели ревью, чтобы не запускать бесконечную проверку отчёта.
- [OpenSpec Task Deliberation](../../.agents/skills/openspec-task-deliberation/SKILL.md) обсуждает явно указанную задачу и допускает решения выполнить, изменить, разделить, удалить или отложить её. Скилл прямо запрещает собственный отчёт, правки файлов и отметку выполнения: результатом является разговор. Одобрение текущего варианта задачи не следует автоматически переносить на существенно изменённую задачу.
- [Текущий Apply](../../.agents/skills/openspec-apply-change/SKILL.md) последовательно выполняет оставшиеся задачи. Ограничение отдельного запуска одной согласованной задачей ещё нужно оформить в контракте будущей автоматизации.
- [Конфигурация OpenSpec](../../openspec/config.yaml) требует промежуточных коммитов и не разрешает архивирование после одной промежуточной фазы. [Git hook](../../lefthook.yaml) ограничивает смешивание изменений OpenSpec с другими файлами в одном коммите; агент коммитов должен учитывать правила репозитория.

## Первичные сведения об интеграциях

Проверка выполнена 2026-09-07 по справке и установленному коду `@getpaseo/cli` версии 0.7.2, с сопоставлением с официальной документацией. Рабочие сессии не создавались и не изменялись; поведение после сбоя daemon и закрытия вкладки экспериментально не проверялось.

- [Документация workspace](https://github.com/getpaseo/paseo/blob/main/public-docs/workspaces.md) описывает workspace как контейнер рабочего каталога и сессий, отображаемых вкладками. Один каталог может использоваться несколькими workspace, поэтому путь репозитория сам по себе ещё не определяет нужный workspace.
- Установлен OpenSpec CLI 1.12.0. В его `dist/commands/workflow/instructions.js` список задач для Apply формируется с полями `id`, `description`, `done`. Поле `id` — последовательный номер записи выдачи; пользовательский номер, например `2.3`, сохраняется в тексте `description`, если присутствует в строке задачи. `dist/utils/task-progress.js` извлекает текст строки с чекбоксом и отметку выполнения, не включая последующие подробности задачи. Следовательно, нужный номер следует извлекать из `description`, а не брать из `id`. Это подтверждено чтением кода; выдача команды для реального активного change в этом репозитории пока не проверялась.
- Справка установленного CLI подтверждает `workspace ls`, запуск через `run --workspace`, назначение названия и меток агента, фильтр `ls --label` и включение архивированных агентов через `ls --all`. Команды и общая организация сессий также описаны в [официальной документации CLI](https://paseo.sh/docs/cli). Названия и метки — возможные средства связи с change и задачей; конкретное соглашение не выбрано.
- В установленном `dist/commands/agent/inspect.js` команда `inspect --json` формирует отдельные поля `Status`, `Archived`, `ArchivedAt`, `CreatedAt` и `UpdatedAt`. Следовательно, состояние выполнения и архивирование технически различаются. Справка отдельно описывает `wait` как ожидание перехода в `idle`, `archive` как мягкое удаление и `delete` как окончательное удаление. Ни один из этих фактов сам по себе не кодирует одобрение задачи человеком.
- [Документация CLI](https://paseo.sh/docs/cli) описывает чтение истории через `logs`, последующие сообщения через `send` и структурированный ответ через `--output-schema`. Они дают возможные средства сопровождения и чтения результата; полнота восстановления истории архивированной сессии пока не проверена.
- Сводный вывод `ls` установленной версии не содержит всех полей исходного состояния агента, а `workspace ls` описан как список активных workspace. Для реализации потребуется проверить достаточность конкретных команд или другого интерфейса Paseo, доступность архивных данных и связь агента с workspace. Наличие данных внутри Paseo ещё не гарантирует их доступность через выбранную команду.
- [Документация ntfy](https://docs.ntfy.sh/publish/#click-action) подтверждает отправку уведомления HTTP-запросом и передачу ссылки в заголовке `Click` / `X-Click`: нажатие открывает указанный URL в браузере или соответствующем приложении. Это соответствует требованию перехода к сессии из уведомления. Конкретный адрес сессии Paseo и его открытие на устройстве пользователя ещё не проверены. Проверка ntfy была чтением документации; уведомления не отправлялись.
- Справка установленного `paseo run` подтверждает отдельные параметры `--provider`, `--model`, `--thinking` и `--mode`. [Документация профилей Paseo](https://paseo.sh/docs/custom-providers#multiple-profiles) описывает несколько именованных записей на основе одного провайдера. Поэтому соответствие пользовательского понятия «профиль» конкретным полям запуска нужно определить по возможностям Paseo, не предполагая наличие универсального флага `--profile`.
- Чтение установленного `@getpaseo/cli` 0.7.2, `dist/commands/agent/run.js`, показало: режим `--output-schema` получает ответ из последнего сообщения или истории агента, проверяет его формат и при повторной попытке отправляет сообщение в ту же сессию. Отдельно различаются ожидание разрешения, ошибка и тайм-аут. Это подтверждает наличие основы для технического протокола, но не доказывает восстановление после потери памяти нашего CLI: повторный запуск `paseo run` создаёт агента, а продолжение существующей сессии должно использовать её обнаруженный идентификатор. Рабочий эксперимент с прерыванием ещё не проводился.

- В установленном Paseo `dist/commands/agent/open.js` получает идентификатор сервера и передаёт его вместе с идентификатором агента механизму открытия Desktop; `dist/commands/open.js` использует `buildAgentDeepLink`. Значит, в Paseo предусмотрена адресация конкретной сессии через ссылку. Сам формат URI и открытие из ntfy на устройстве пользователя пока не проверены.

## Выводы из сопоставления намерений и текущих правил

- **Цикл повторного чтения соответствует изменяемому процессу.** После обсуждения могут измениться задачи, фазы или замечания; заранее вычисленная цепочка действий быстро устаревает.
- **Paseo — допустимый источник продолжения.** Одинаковое файловое состояние до и после обсуждения не доказывает невозможность восстановления: нужное различие может сохраняться в сессиях Paseo. Дополнительные записи в OpenSpec для решения этой проблемы не согласованы и противоречат уточнённому ограничению.
- **Возобновление требует различимых состояний в разрешённых источниках.** CLI должен распознать сессию нужного change, действия и задачи после потери собственных идентификаторов из памяти. Существование похожего названия или последней по времени сессии ещё не доказывает правильность такого сопоставления.
- **Закрытие вкладки и решение по задаче — разные факты.** Пользователь подтвердил закрытие как сигнал. После него нужно определить итог обсуждения: разбор может закончиться изменением или отказом от задачи. Конкретный способ чтения результата и его сохранность пока не установлены.
- **Происхождение сессии и участие человека — разные признаки.** Сессия, созданная оркестратором, может быть автономной или требовать человеческого решения; автономная сессия может потребовать помощи при затруднении. Участие пользователя в такой сессии не выводит её из управления CLI. Вручную созданная пользователем сессия целиком исключена из учёта сессий процесса. Источником состояния файлов по-прежнему служит актуальный репозиторий после обычной работы.
- **Тип действия, рабочее поручение и технический протокол имеют разные роли.** Тип определяет место сессии в процессе и выбирает настройки агента из конфигурации. Встроенный промпт задаёт содержательную работу с актуальным предметом поручения. Техническое взаимодействие нужно для распознавания готовности или результата. Оба вида промптов принадлежат CLI; конкретный способ получения итогового ответа ещё не выбран.
- **Занятость агента и завершённость шага различаются.** Агент обсуждения может закончить свой ответ и ждать человека; это не освобождает следующий шаг Apply. С другой стороны, наличие открытой вкладки само по себе не доказывает, что агент сейчас выполняет работу. Восстановление должно учитывать и состояние выполнения, и незавершённое взаимодействие текущего шага.
- **Готовность к человеку — промежуточное событие текущего шага.** Завершение первоначальной работы агента вызывает уведомление, но сессия остаётся открытой для пользователя и следующий шаг не начинается. При постоянном наблюдении нужно различать наступление готовности и очередное чтение того же состояния, чтобы не отправлять уведомление на каждом проходе цикла. После перезапуска при неизвестном результате предыдущей отправки и сохранившейся потребности в человеке согласована повторная отправка.
- **Проверка собственных незавершённых действий предшествует новому поручению.** Это относится и к агенту коммитов: после прерывания сначала нужно разобраться со своей существующей сессией. После ожидания своего агента или решения человека нужно заново прочитать репозиторий, а не продолжать действие, выбранное по состоянию до ожидания. Пользовательские сессии не являются основанием для ожидания.
- **Открытая сессия не доказывает незавершённость поручения.** CLI может прерваться после выполнения агентом работы, но до проверки результата или закрытия сессии. При восстановлении необходимо проверить существующее поручение и его результат, прежде чем запускать его повторно. Конкретная гарантия повторного выполнения ещё не выбрана.
- **Факт проведения ревью и его замечания имеют разные источники.** Закрытие соответствующей собственной сессии означает для CLI, что ревью проведено. Открытые проблемы читаются из файлов ревью и могут сохраняться после закрытия сессии. Это позволяет не запускать повторно уже проведённое ревью только потому, что задачи фазы ещё не начали выполнять.
- **Выполнение поручения ревью не означает отсутствие замечаний.** Агент может полностью провести проверку и найти проблемы: само поручение выполнено, а следующим действием становится их разбор. Подтверждение выполнения автономного поручения предшествует закрытию сессии; при последующих проходах факт проведённого ревью определяется по её закрытию.
- **Окончание задачи, фазы и всего процесса — разные факты.** Последний отмеченный пункт задач ещё не доказывает завершение: может оставаться ревью, разбор замечаний, корректирующая работа или непредставленная фаза плана. Ошибка получения списка задач или чтения плана не равнозначна отсутствию работы. Отдельное архивирование не требуется для успешного окончания CLI.
- **Восстановление включает сверку с Paseo перед новым запуском.** После сбоя CLI агент потенциально может оставаться активным до появления изменений в файлах. Проверка существующих сессий должна позволять обнаружить такую работу. Гарантии сохранности данных и поведение при недоступности Paseo остаются открытыми.

## Открытые вопросы

- Какова детализация «каждого шага» в логах: какие сообщения нужны о действиях workflow, технических проверках и повторных опросах источников? Как показывать длительное ожидание, какой формат вывода выбрать и как сохранять его для последующего просмотра? Цель уже определена: по `stdout` понимать историю действий и текущее занятие CLI; конкретные правила вывода пока не выбраны.
- Как обнаруживать нужные файлы независимо от схемы change и обрабатывать отсутствие ещё не созданного пакета задач или отчёта? Связь задач с фазами уже определена через первую часть номера; служебные записи для CLI не добавляются.
- Как надёжно находить единственный workspace выбранного change и отличать созданные CLI сессии от пользовательских? Достаточно ли формата `title`, как учитывать переименование и какие обычные средства Paseo сохранят связь с действием, задачей и повторной попыткой?
- Как предотвращать повторный запуск собственного действия, если два экземпляра CLI одновременно пытаются продолжить один change? Поведение при таком запуске ещё не определено; собственные сессии пользователя не входят в эту координацию.
- Что именно означает «продолжить с того же места»: восстановить ту же незавершённую сессию, заново выполнить безопасную проверку или никогда не повторять уже начатое действие? Какие повторения приемлемы пользователю?
- Какой факт Paseo соответствует закрытию вкладки в используемом приложении и версии? Как отличить окончание обсуждения от положительного решения по задаче, в том числе при отказе, откладывании, удалении или разделении задачи?
- Как восстанавливается доступ к истории и архивированным сессиям после сбоя CLI или daemon? Что происходит после окончательного удаления агента или архивирования workspace, и как продолжать при недоступных либо неоднозначных данных? Наличие команд проверено, гарантии этих сценариев — ещё нет.
- Какими форматами ответов и наблюдаемыми фактами подтверждать полное завершение каждого вида автономного поручения перед автоматическим закрытием сессии? Общий принцип согласован; набор проверок, восстановление после прерывания и поведение при непонятном ответе или противоречии с артефактами ещё не определены.
- Как определять границы закоммиченной реализации для ревью отдельной задачи? Как проводить ревью задачи, которая только проверяет готовность фазы и не меняет код? Факт проведения соответствующего ревью для CLI уже определён: его собственная сессия закрыта.
- Как выбирать следующую работу после разделения или удаления обсуждаемой задачи, появления исправлений по ревью либо изменения незавершённых фаз? Текущие правила защищают выполненные задачи от переписывания, но точный приоритет новых действий ещё не согласован.
- Что делать с частично выполненной задачей и грязным рабочим деревом после прерывания: всегда сначала коммитить или сначала возобновлять исполнителя? Какой контекст позволяет агенту сформировать корректные коммиты?
- Как применить правило одного работающего агента к родительской сессии и внутренним субагентам ревью? Текущий скилл требует независимых проверяющих в свежем контексте; независимость контекста сама по себе не требует одновременного выполнения проверок.
- Как по состоянию Paseo определить, что закончена именно первоначальная работа по стартовому запросу и сессия готова к пользователю? Как получать ссылку, открывающую нужную сессию на его устройстве?
- Как обрабатывать недоступность ntfy и повторять запросы при длительном сбое сервиса без собственного журнала выполнения CLI? Повторная отправка после перезапуска при неизвестном результате уже согласована; интервалы повторов, адрес сервиса и настройки доступа пока не определены.
- Как назвать конфигурационный файл в рабочем репозитории и его ключи, какие параметры обязательны и как обрабатывать отсутствующие или неподдерживаемые значения? Провайдеры и модели задаются пользователем по типам сессий, а не выбираются внутри CLI.
- Как устроить технический протокол готовности и результата сессии? Первоначальные и служебные промпты входят в CLI, но необходимость отдельного завершающего запроса и конкретный формат ответа пока не выбраны.
- Как сопоставить параметры конфигурации, включая профиль и reasoning, с возможностями Paseo и выбранного провайдера? Как применять правки конфигурации во время долгоживущего процесса и при возобновлении уже созданной сессии?
