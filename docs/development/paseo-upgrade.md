# Обновление активного контракта Paseo

Оркестратор одновременно поддерживает ровно один точный выпуск Paseo CLI и
локального daemon. Исполняемый источник этой совместимости —
`internal/paseo/internal/paseocli`: там находятся версия, аргументы команд,
wire-проекции JSON, системная семантика provider и режима полного доступа и
формат deep-link. Это руководство описывает повторяемую замену контракта, но не
является вторым источником исполняемого поведения.

## Неизменяемые границы

- Новый выпуск заменяет активный контракт. Нельзя добавлять реестр версий,
  SemVer-диапазон, ветви обратной совместимости или capability probing вместо
  точной квалификации.
- Если требуемые возможности и их семантика сохранились, доменный интерфейс
  `internal/paseo`, ядро сопровождения и production-команда не меняются. Если
  для миграции нужно изменить их поведение, следует остановиться и оформить
  отдельное OpenSpec-изменение.
- Оркестратор проверяет параметры собственного вызова Paseo. Установленные
  пользователем плагины и их последующие преобразования считаются доверенной
  политикой среды: миграция не добавляет `plugin ls`, проверку топологии или
  попытку доказать эффективную конфигурацию после plugin lifecycle.
- Прямой протокол daemon, SDK и разбор человекочитаемого вывода не заменяют
  JSON-команды CLI.

## 1. Выбрать и исследовать точный выпуск

1. Зафиксировать один целевой тег Paseo и точный предыдущий тег активного
   контракта.
2. Сравнить официальные изменения между тегами и прочитать исходники целевого
   тега для всей используемой поверхности: `status`, `provider ls`,
   `provider models`, `workspace ls`, `workspace create`, `ls`, `inspect`,
   `wait`, `run` и `archive`.
3. Отдельно подтвердить формат deep-link и системную семантику режима полного
   доступа встроенного provider. Для Codex должны быть доказаны передаваемый ID
   режима, `approvalPolicy` и `sandbox`, а не только человекочитаемое название.
4. Проверить, что значимые поля, закрытые состояния и межполевые инварианты
   сохранились. Аддитивные неиспользуемые поля допустимы; изменение значимой
   семантики требует пересмотра спецификации, а не ослабления декодера.

Для текущего контракта ссылки на точный upstream-тег находятся рядом с
соответствующими структурами и правилами в `paseocli`. При замене выпуска эти
ссылки обновляются вместе с кодом.

## 2. Заменить активный адаптер

1. В `internal/paseo/internal/paseocli/contract.go` заменить точные версии CLI
   и daemon и доказанную системную семантику полного доступа.
2. В файлах команд этого же пакета обновить только изменившиеся аргументы,
   wire DTO, закрытые значения и проверки инвариантов. Формирование deep-link
   остаётся в `link.go`.
3. Обновить pin `npm:@getpaseo/cli` в `mise.toml`, чтобы локальная и CI-проверка
   устанавливали квалифицируемый выпуск. Этот pin выбирает инструмент стенда, но
   production-код принимает версию только из `activeContract`.
4. Не добавлять версию или production-режим в
   `internal/paseo/testpaseo`. Стенд получает их через `paseocli.ActiveContract`
   и интеграционный контракт, поэтому обычная миграция не требует второй копии.

## 3. Переснять и проверить fixtures

На изолированном daemon целевого выпуска получить реальный JSON каждой
используемой команды и обновить каталог
`internal/paseo/internal/paseocli/testdata/v<версия>/`:

- `version.txt` и `status.json`;
- `provider-ls.json` и `provider-models-codex.json`;
- `workspace-ls.json` и `workspace-create.json`;
- `session-ls.json`, `session-inspect.json`, `session-wait.json`,
  `session-run.json` и `session-archive.json`.

Перед сохранением обезличить временные пути, владельца, hostname, PID,
`serverId`, ID workspace и сессии, не удаляя известные поля ответа. Fixture с
предыдущей версией и хотя бы одна fixture со значимым нарушением формы остаются
отрицательными доказательствами. Затем обновить тестовый указатель каталога и
убедиться, что каждая fixture проходит production-декодер либо ожидаемо им
отклоняется.

```sh
go test ./internal/paseo/internal/paseocli -count=1
go test ./internal/paseo/... -count=1
```

## 4. Доказать locality

Автоматическая проверка должна подтвердить, что процессный стенд находится в
`internal/paseo/testpaseo`, а детали production-контракта не вышли из
`paseocli`:

```sh
go test ./internal/paseo/internal/paseocli \
  -run TestАктивныйКонтрактPaseoЛокализованВоВнутреннемАдаптере -count=1
rg -n 'internal/testpaseo' --glob '*.go' .
```

После миграции отдельно найти прежнюю версию в исполняемых Go-файлах. Команда
ниже должна завершиться без совпадений; значение переменной меняется на прежний
выпуск конкретной миграции:

```sh
old_paseo_version='0.7.2'
rg -n --fixed-strings "$old_paseo_version" cmd internal \
  --glob '*.go' --glob '!**/*_test.go'
```

Упоминания прежнего выпуска в документации, истории change, отрицательных
fixtures и тестах отказа допустимы: они объясняют миграцию или доказывают
несовместимость и не участвуют в production-решении. Упоминание активной версии
в `mise.toml` также является pin инструмента стенда, а не альтернативным
контрактом runtime.

## 5. Повторно квалифицировать поведение

Сначала выполнить обычные проверки репозитория:

```sh
go test ./...
go test -race ./...
go vet ./...
go build ./cmd/openspec-apply-orchestrator
```

Затем убедиться, что доступный в `PATH` `paseo` и запущенный стендом daemon
имеют точную новую версию, и прогнать весь процессный контур последовательно:

```sh
go test -p=1 -count=1 -tags=paseo_integration \
  ./internal/paseo/... \
  ./internal/orchestrator/... \
  ./cmd/openspec-apply-orchestrator/...
```

Прогон считается квалификацией только когда он повторно подтверждает:

- подготовку staged, tracked и untracked изменений с точными проверенными
  настройками полного доступа и без fallback;
- восстановление того же полного ID сессии после прерывания процесса и
  штатного перезапуска daemon без повторного `run` и чтения входов создания;
- один `run` при неопределённом результате создания и продолжение только после
  явного подтверждения видимой собственной сессии;
- единственный блокирующий `wait`, отсутствие технических чтений Paseo внутри
  ожидания и строгий порядок свежих `workspace ls`, фильтрованных `ls` и
  `inspect` после его возврата;
- чистый Git без изменения `HEAD`, `workspace create`, `run` или `archive`,
  когда поручение не требуется;
- грязный Git, ошибку агента, запрос разрешения и ошибки источников без
  автоматической замены сессии, повтора мутации или ослабления режима;
- пользовательский plugin hook без запроса его топологии оркестратором и без
  расширения границы проверяемых параметров вызова.

Если любой сценарий требует изменения доменной семантики, миграция не считается
локальной и не завершается исправлением теста под новое поведение. Нужно
зафиксировать обнаруженное различие в OpenSpec и отдельно решить судьбу
контракта.
