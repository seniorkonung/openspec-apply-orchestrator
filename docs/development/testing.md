# Уровни проверок и системные сценарии

Проверки оркестратора следуют [ADR 0004](../adr/0004-system-tests-cover-user-journeys.md):
каждый технический вариант имеет один основной владеющий уровень, а тесты с
тегом `paseo_integration` подтверждают только внешний контракт Paseo или
целостный пользовательский путь через production-бинарник. Тяжёлый тест не
дублирует матрицу нижнего уровня ради повторной проверки того же условия.

## Карта владеющих уровней

| Поведение | Основной уровень | Доказательство |
|---|---|---|
| Чтение единственного снимка, обязательные поля, неизвестные поля, варианты канала, пять приоритетов и `default` | `internal/config` | `config_test.go` с управляемыми файлами без Paseo и HTTP |
| Точный HTTP-контракт ntfy, авторизация, отсутствие запроса без токена, запрет redirect, тайм-ауты, предел ответа и статусы | `internal/notify` | `ntfy_test.go` с локальным `httptest` |
| Выбор действия по состоянию сессии и Git, три причины участия человека, ожидание, закрытие, дедупликация и расписание повторов | `internal/orchestrator` | `commit_preparation_test.go` и `commit_preparation_intervention_test.go` с управляемыми gateway и часами |
| Linux-local граница, канонические корни, поддерживаемые файловые системы и локальный lock change | `internal/ownership` | `environment_test.go` и `lock_test.go`, включая отдельный вспомогательный процесс lock |
| Аргументы CLI, wire JSON, значимые состояния, точные фильтры, полный доступ, неопределённые мутации и deep-link | `internal/paseo/internal/paseocli` и `internal/paseo` | контрактные fixtures и подменный исполняемый файл |
| Сборка зависимостей, порядок preflight, коды завершения, безопасный stdout и локальный heartbeat без технического опроса | `cmd/openspec-apply-orchestrator` без build tag | `prepare_commits_test.go` и `reporting_test.go` с подменными адаптерами |
| Совместимость точного выпуска CLI и daemon, реальное создание и видимость сессии после перезапуска daemon | `internal/paseo` с `paseo_integration` | один связный поток `TestРеальныйPaseoКвалифицируетСозданиеИВосстановлениеСессии` |
| Связность production-бинарника, Git, OpenSpec, Paseo и локального HTTP-приёмника в пользовательской истории | `cmd/openspec-apply-orchestrator` с `paseo_integration` | именованный сценарий с одним исходным положением и пользовательским результатом |

Из этой карты следуют конкретные владельцы удалённых process-вариантов:

- отсутствующий файл, повреждённый JSON, отсутствующий канал и недопустимый
  приоритет принадлежат `internal/config`; восстановление без пригодных входов
  создания дополнительно проверяет обычный тест команды;
- отсутствующий токен, сетевой отказ, повтор, redirect и неизменность HTTP-полей
  принадлежат `internal/notify`; расписание повтора и неизменность эпизода —
  `internal/orchestrator`;
- грязный Git после хода, ошибка агента и запрос разрешения принадлежат таблице
  переходов `internal/orchestrator`, а их русское представление — репортёру
  команды;
- неизвестные provider, model и reasoning, профиль без полного доступа,
  повреждённый каталог, неверный ID `wait` и ошибки свежего чтения принадлежат
  `internal/paseo` и активному `paseocli`-адаптеру;
- неподдерживаемая файловая система и конкуренция локальных процессов принадлежат
  `internal/ownership` и проверяются без запуска daemon Paseo;
- запрет технических чтений во время блокирующего `wait` проверяется
  управляемым gateway команды и тестами ожидания Paseo. Реальный daemon не
  нужен для перебора этого внутреннего порядка;
- запрет повторения неопределённого `run` проверяется тестами мутаций Paseo, а
  восстановление уже видимой сессии остаётся отдельной пользовательской
  process-историей.

## Каталог тяжёлых проверок

Реальный Paseo используется одним связным квалификационным потоком в
`internal/paseo/recovery_integration_test.go`. Он проверяет точную совместимую
среду, один запрос создания при включённом пользовательском plugin, отсутствие
запроса plugin-топологии, серверные фильтры и восстановление того же workspace
и той же видимой собственной сессии после штатного перезапуска daemon. Варианты
ошибок wire-контракта остаются в fixtures активного адаптера.

Production-пакет содержит следующие целостные истории:

- чистый Git не вызывает поручение, а staged, tracked и untracked работа
  сохраняется одним поручением;
- после прерывания во время работы или после коммита продолжается та же сессия;
- после перезапуска daemon восстанавливается та же видимая сессия;
- после неопределённого `run` новый процесс продолжает подтверждённую видимую
  сессию без повторного поручения;
- после уведомления пользователь продолжает работу в той же сессии;
- закрытие с грязным Git допускает новую явную попытку без восстановления
  архивированной истории;
- после сбоя доставки текущий процесс сохраняет свой снимок, а новый процесс
  применяет новый снимок к той же сессии.

Файлы с тегом могут содержать общие помощники стенда, но не добавляют отдельное
доказательство, пока в них нет именованного `Test...`.

## Когда добавлять системный сценарий

Новый тест с `paseo_integration` допустим, только если одновременно выполнены
все условия:

1. Проверяемое свойство нельзя надёжно доказать владельцем с fixture,
   подменным процессом, управляемыми часами или локальным HTTP-сервером.
2. Сценарий проходит границу production-бинарника или подтверждает фактический
   контракт точного выпуска Paseo.
3. Имя выражает пользовательский результат, а тело имеет одно наблюдаемое
   исходное положение, одно развитие истории и один итог.
4. В тесте нет таблицы значений конфигурации, HTTP-статусов, wire-ответов или
   внутренних состояний. Такие варианты сначала добавляются на владеющий
   уровень.
5. Сценарий изолирует репозиторий, workspace, сессии и журнал, имеет deadline и
   освобождает созданные стендом процессы.

Если новый случай можно выразить строкой в существующей технической таблице,
он почти наверняка принадлежит обычному тесту, а не process-каталогу.

## Команды

Обычные проверки не требуют Paseo и запускают все технические матрицы:

```sh
go test -count=1 ./...
go test -race ./internal/config/... ./internal/notify/... ./internal/orchestrator/... ./internal/ownership/... ./internal/paseo/...
```

Один внешний поток квалификации Paseo запускается отдельно:

```sh
go test -p=1 -parallel=1 -count=1 -tags=paseo_integration \
  -run '^TestРеальныйPaseoКвалифицируетСозданиеИВосстановлениеСессии$' \
  ./internal/paseo
```

Текущий каталог production-историй запускается последовательно единой
командой, которая один раз собирает production-бинарник и не запускает
технические проверки нижних уровней:

```sh
mise run test-paseo-scenarios
```

Требования к установленному Paseo и изоляции daemon описаны в
[руководстве по совместимости](paseo-compatibility.md).
