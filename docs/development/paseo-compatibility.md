# Интеграционная совместимость с Paseo

Производственный адаптер и интеграционный стенд поддерживают Paseo CLI и
локальный daemon версии `0.8.0-beta.1`. Адаптер обращается только к установленному
исполняемому файлу `paseo`: запускает команды как отдельные процессы без shell,
проверяет их JSON и не подключается к внутреннему протоколу или WebSocket
daemon. Исполняемый источник версии, команд, wire-проекций, системной семантики
и deep-link находится только в `internal/paseo/internal/paseocli`; порядок его
следующей замены описан в [руководстве по обновлению](paseo-upgrade.md).

## Запуск проверки

Для проверки нужен Linux, доступный в `PATH` `paseo` версии `0.8.0-beta.1` и Go из
`go.mod`. Пользовательский daemon можно не останавливать: стенд создаёт отдельный
временный `PASEO_HOME`, Unix-socket, workspace и настоящий временный Git-репозиторий
с OpenSpec change. Relay, MCP и web UI для тестового daemon отключены. Управляемый
ACP-провайдер не обращается к внешней модели; в сценарии подготовки коммитов он
фиксирует изменения обычными командами Git.

```sh
go test -p=1 -parallel=1 -count=1 -tags=paseo_integration ./internal/paseo/... ./cmd/...
```

Стенд в `internal/paseo/testpaseo` сам собирает тестовый провайдер и отдельные
процессы сопровождения, запускает daemon и останавливает его при завершении
теста. В подробном выводе проверки указываются фактически обнаруженные версия
Paseo, `serverId`, полный ID workspace и ID сессий. Эти значения создаются
заново для каждого запуска и не являются постоянной конфигурацией проекта.

## Что подтверждает стенд

Один связный поток модуля Paseo подтверждает только свойства внешнего процесса,
которые нельзя заменить fixture: совместимые CLI и daemon, фактический запрос
создания при включённом пользовательском plugin, видимость сессии через
серверные фильтры и восстановление того же workspace и сессии после штатного
перезапуска daemon.

Тесты production-команды проверяют целостные пользовательские истории: отсутствие
работы и подготовку всех видов Git-изменений, восстановление после прерывания,
перезапуска daemon и неопределённого `run`, продолжение работы после уведомления,
новую попытку после закрытия с грязным Git и применение нового снимка после
перезапуска процесса.

Матрицы конфигурации, HTTP-доставки, переходов состояния и wire-ответов не
повторяются с настоящим daemon. Их владельцы, точные тесты и правила добавления
нового системного сценария перечислены в [карте проверок](testing.md).

## Разделение тестового и производственного режима

Сопоставление `oa-integration` → `integration-unrestricted` компилируется только
с тегом `paseo_integration`. Оно даёт тестовому ACP-провайдеру семантику
`approvalPolicy=never` и `sandbox=danger-full-access`, необходимую для реального
Git в изолированном стенде. Обычная production-сборка его не содержит.

Производственный контракт проверяется отдельно точными unit-фикстурами:
совместимая пара Paseo `0.8.0-beta.1` и `codex` обязана преобразовываться в
`--mode full-access` с той же семантикой `never`/`danger-full-access`. Любое
непроверенное сопоставление отклоняется до `run`; fallback на другой режим
запрещён.

Стенд получает точную версию и тестовый unrestricted-режим из активного и
интеграционного контрактов `paseocli`, а не хранит их вторую копию. Проверка
locality запрещает вынос production-версии, аргументов команд, wire DTO,
provider/mode semantics и deep-link в ядро или production-команду. Установленные
пользователем плагины остаются доверенной политикой Paseo: единственный
квалификационный поток подтверждает переданные оркестратором параметры, но не
превращает plugin-топологию в условие совместимости.

## Граница восстановления

Стенд доказывает восстановление уже видимой активной собственной сессии. Он не
устраняет принятое окно между приёмом команды создания daemon и появлением
сессии в результатах чтения. После неопределённого `run` пользователь должен
проверить состояние Paseo перед новым явным запуском. Предварительное
резервирование, собственный журнал прогресса и автоматический повтор мутации не
используются.

Process-каталог использует только локальный HTTP-приёмник ntfy-контракта. Он не
заменяет проверку открытия и очистки уведомления на пользовательском устройстве.
