# Интеграционная совместимость с Paseo

Производственный адаптер и интеграционный стенд поддерживают Paseo CLI и
локальный daemon версии `0.7.2`. Адаптер обращается только к установленному
исполняемому файлу `paseo`: запускает команды как отдельные процессы без shell,
проверяет их JSON и не подключается к внутреннему протоколу или WebSocket
daemon.

## Запуск проверки

Для проверки нужен Linux, доступный в `PATH` `paseo` версии `0.7.2` и Go из
`go.mod`. Пользовательский daemon можно не останавливать: стенд создаёт отдельный
временный `PASEO_HOME`, Unix-socket, workspace и настоящий временный Git-репозиторий
с OpenSpec change. Relay, MCP и web UI для тестового daemon отключены. Управляемый
ACP-провайдер не обращается к внешней модели; в сценарии подготовки коммитов он
фиксирует изменения обычными командами Git.

```sh
go test -p=1 -count=1 -tags=paseo_integration ./internal/paseo/... ./internal/orchestrator/... ./cmd/...
```

Стенд сам собирает тестовый провайдер и отдельные процессы сопровождения,
запускает daemon и останавливает его при завершении теста. В подробном выводе
проверки указываются фактически обнаруженные версия Paseo, `serverId`, полный ID
workspace и ID сессий. Эти значения создаются заново для каждого запуска и не
являются постоянной конфигурацией проекта.

## Что подтверждает стенд

- `paseo --version` и `paseo status --json` подтверждают совместимые версии CLI
  и daemon, локальность, владельца и непустой `serverId` до мутаций.
- Один `paseo run --background --json` передаёт первоначальное поручение, полный
  ID workspace и полный набор меток принадлежности. После штатного перезапуска
  daemon тот же workspace и та же видимая активная собственная сессия находятся
  через `workspace ls`, широкий и точный фильтры `ls` и последующий `inspect`.
- Новые процессы сопровождения восстанавливают работающую сессию, завершившийся
  ход и запрос разрешения. Проверки до и после `archive` различают видимую
  активную сессию и корректное отсутствие активной сессии.
- Ручная сессия и собственная сессия другого change не выбираются и не
  архивируются. Неподдерживаемая файловая система отклоняется до команд
  `workspace create`, `run` и `archive`.
- Потеря проверяемого JSON-ответа на `run` даёт неопределённый исход. Текущий
  процесс не повторяет создание, а новый процесс способен продолжить уже
  видимую сессию.
- Production-команда на чистом Git завершается без агента, а при одновременно
  отслеживаемых, индексированных и неотслеживаемых изменениях ровно один раз
  передаёт встроенное поручение и получает чистый Git с новым коммитом.
- Журнал реальных вызовов CLI подтверждает проверенный режим стенда
  `integration-unrestricted`, единственный блокирующий `wait`, отсутствие
  inspect-polling и свежее чтение workspace, сессии и `inspect` перед `archive`.
- Та же активная собственная сессия переживает отдельные остановки процесса во
  время работы на грязном Git и после создания коммита, а затем восстанавливается
  без повторного `run`, чтения каталога провайдеров или зависимости от удалённого
  конфига, отсутствующего канала либо неподдерживаемых текущих provider, model и
  reasoning.
- Недостоверные настройки, профиль без проверенного сопоставления, повреждённый
  каталог, ошибка свежего чтения, ошибка агента, запрос разрешения и неверный
  результат `wait` завершаются без автоматической замены или повтора сессии.

## Разделение тестового и производственного режима

Сопоставление `oa-integration` → `integration-unrestricted` компилируется только
с тегом `paseo_integration`. Оно даёт тестовому ACP-провайдеру семантику
`approval=never` и `sandbox=danger-full-access`, необходимую для реального Git в
изолированном стенде. Обычная production-сборка его не содержит.

Производственный контракт проверяется отдельно точными unit-фикстурами:
совместимая пара Paseo `0.7.2` и `codex` обязана преобразовываться в
`--mode full-access` с той же семантикой `never`/`danger-full-access`. Любое
непроверенное сопоставление отклоняется до `run`; fallback на другой режим
запрещён.

## Граница восстановления

Стенд доказывает восстановление уже видимой активной собственной сессии. Он не
устраняет принятое окно между приёмом команды создания daemon и появлением
сессии в результатах чтения. После неопределённого `run` пользователь должен
проверить состояние Paseo перед новым явным запуском. Предварительное
резервирование, собственный журнал прогресса и автоматический повтор мутации не
используются.

Стенд не проверяет внешнюю доставку уведомлений: локальный HTTP-приёмник и
наблюдаемость канала относятся к следующей фазе change.
