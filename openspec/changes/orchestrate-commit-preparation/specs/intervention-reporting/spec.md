## ADDED Requirements

### Requirement: Передача затруднения в текущую сессию

Когда агент перестал выполнять ход, но Git остаётся грязным, а также при запросе разрешения Paseo или ошибке агента CLI MUST сообщать необходимость участия пользователя и объяснять наблюдаемую причину. Текущая собственная сессия MUST становиться целью перехода из уведомления без показа её непрозрачного идентификатора или сырого deep-link в пользовательских заголовке и тексте. CLI MUST сохранять ту же сессию и наблюдать её, пока пользователь и агент продолжают работу; новый агент только ради передачи человеку MUST NOT создаваться.

Ручное закрытие переданной сессии MUST завершать её сопровождение и вызывать свежую проверку Git. Чистое дерево после закрытия MUST означать успех, грязное — неуспех текущего запуска. Последующий явный запуск при грязном Git и отсутствии активной собственной сессии MUST считаться новой попыткой, а не продолжением закрытой сессии.

Для уже ожидающей человека idle-сессии CLI MUST NOT вызывать `paseo wait` в непрерывном цикле, поскольку команда немедленно возвращается без нового хода. CLI MUST с ограниченной частотой перечитывать фильтры и `inspect`: возобновление работы MUST вернуть сопровождение к блокирующему `paseo wait`, а ручное закрытие MUST вызвать проверку Git. Неизменившееся ожидание MUST NOT вызывать новое уведомление на каждом чтении.

#### Scenario: Агенту требуется помощь
- **GIVEN** агент перестал выполнять ход, а Git остаётся грязным
- **WHEN** CLI перечитывает состояние сессии и репозитория
- **THEN** CLI показывает безопасные заголовок и причину, а переход из уведомления открывает текущую сессию при продолжении сопровождения того же поручения

#### Scenario: Пользователь закрыл сессию без результата
- **GIVEN** сессия передана человеку и Git остаётся грязным
- **WHEN** пользователь закрывает её
- **THEN** CLI повторно проверяет Git и завершает текущий запуск неуспешно без постоянной блокировки следующей явной попытки

#### Scenario: Пользователь возобновил ход агента
- **GIVEN** idle-сессия передана человеку и остаётся активной
- **WHEN** пользователь отправляет агенту продолжение работы
- **THEN** CLI обнаруживает работающий ход при очередном ограниченном чтении и снова ожидает его через одну блокирующую команду `paseo wait`

### Requirement: Доставка уведомлений через настроенный канал

CLI MUST формировать транспортно-нейтральное уведомление только при наступлении потребности в человеке у известной активной собственной сессии и передавать его одному настроенному адаптеру. Событие MUST содержать change, наблюдаемую причину и проверенные идентификатор и ссылку этой сессии; адаптер MUST использовать идентификатор только как внутренний контекст и MUST NOT показывать его пользователю вместо осмысленного названия поручения. Перед созданием нового production-поручения формат конфигурации версии 1 MUST требовать один канал как дискриминированный вариант `notifications.intervention` с обязательными `type` и `url`; единственным поддерживаемым значением `type` MUST быть `ntfy`. Необязательное `notifications.intervention.priority` MUST принимать только `min`, `low`, `default`, `high` или `max`, а при отсутствии MUST разрешаться как `default`. Если активной собственной сессии нет, Git требует нового поручения, а канал отсутствует, CLI MUST сообщить ошибку конфигурации с путём `notifications.intervention`, завершиться с кодом `2` и MUST NOT создавать или изменять workspace и сессии Paseo. Запуск агента, очередное чтение неизменного ожидания или препятствие до обнаружения известной активной собственной сессии MUST NOT вызывать уведомление.

Адаптер ntfy MUST отправлять HTTP-уведомление по настроенному адресу. Каждый запрос MUST передавать заголовок `Title` в точной форме `Подготовка коммитов: <change>`, безопасный текст наблюдаемой причины, ровно одно действие ntfy типа `view` с точной меткой `Открыть сессию`, проверенным Paseo deep-link текущей сессии как целью и обязательным `clear=true`, а также разрешённое значение приоритета в `Priority`. Верхнеуровневый `Click` MUST NOT передаваться, чтобы у уведомления не оставалось отдельного перехода в сессию без очистки. `Title`, текст и метка действия MUST NOT содержать непрозрачный ID сессии или сырой deep-link; активация действия MUST просить клиент ntfy открыть текущую сессию и очистить уведомление, то есть отметить его прочитанным и убрать из панели. Передача `clear=true` MUST быть неизменной гарантией адаптера, MUST NOT настраиваться пользователем и MUST NOT добавлять поле `clear` в `notifications.intervention`. Прекращение отдельного настойчивого звука MUST NOT входить в гарантию отправляющего адаптера: воспроизведение и остановка такого звука принадлежат поведению клиентского приложения ntfy. Необязательное `notifications.intervention.tokenEnv` MUST содержать только имя переменной окружения: при его отсутствии запрос MUST отправляться без авторизации, а при его наличии Bearer-токен MUST читаться из этой переменной только для отправки. Литеральные токены и произвольные секретные поля в JSON MUST отклоняться. Если указанная переменная отсутствует или пуста, CLI MUST NOT выполнять HTTP-запрос, MUST показать ошибку доставки локально и MUST продолжить наблюдение за поручением. Адаптер MUST NOT следовать HTTP-перенаправлениям независимо от наличия `tokenEnv`: любой ответ `3xx` MUST считаться неподтверждённой доставкой, а адрес из `Location` MUST NOT становиться целью второго запроса.

В поддерживаемой личной Linux-local среде `openspec-apply-orchestrator.json`, включая полученные из Git и выполненные full-access агентом изменения, MUST считаться доверенной пользовательской политикой выбора адреса доставки, `tokenEnv` и приоритета. CLI MUST NOT требовать отдельного подтверждения, внешнего trust store или списка разрешённых получателей. При запуске CLI MUST не более одного раза прочитать этот файл и сохранить неизменяемый снимок содержимого либо ошибку чтения; ни разрешение канала, ни повтор доставки MUST NOT перечитывать файл в том же процессе. Для нового поручения проверенный канал MUST быть получен из снимка до первой мутации Paseo. Для существующей сессии канал MUST разрешаться из того же снимка только при фактической потребности в человеке, а наличие и корректность канала MUST NOT быть условием восстановления. Поддерживаемая эксплуатация предполагает отдельный заменяемый токен уведомлений, раскрытие которого приводит только к спаму и пересозданию канала, а безопасные заголовок, сообщение и deep-link локальной Paseo-сессии не считаются значимыми конфиденциальными данными.

Наличие и корректность канала в снимке запуска MUST NOT быть предварительным условием обнаружения, наблюдения, передачи человеку либо архивирования уже существующей активной собственной сессии. Если при наступлении потребности в человеке снимок не содержит корректного канала, CLI MUST показать локальную ошибку доставки, причину потребности, ссылку на известную сессию и указание исправить конфигурацию и перезапустить CLI; CLI MUST сохранить и продолжить наблюдать ту же сессию и MUST NOT создавать замену. Исправление файла MUST NOT изменять поведение уже работающего процесса. Этот отказ доставки MUST NOT считаться поддерживаемым режимом работы только через stdout для создания новых поручений.

Неуспешная доставка через успешно разрешённый адаптер MUST быть видна в stdout; повторные попытки через тот же адаптер и снимок MUST иметь ограниченную частоту, сохранять те же `Title`, текст, очищающее действие `Открыть сессию` и `Priority`, не добавлять `Click` и не останавливать наблюдение за поручением. Невозможность разрешить адаптер из снимка MUST NOT вызывать повторное чтение конфигурации. CLI MUST NOT объявлять доставку успешной без подтверждения настроенного адаптера. После перезапуска новый процесс MUST получить новый снимок, сначала восстановить ту же видимую активную собственную сессию и при сохраняющейся потребности отправить уведомление с настройками нового снимка; при неизвестном результате прошлой отправки такой дубль допустим. Уведомления и логи MUST NOT раскрывать токены доступа, полный приватный адрес канала, промпты, содержимое файлов или полную историю разговора.

#### Scenario: Препятствие возникло до известной сессии
- **GIVEN** CLI не обнаружил известную активную собственную сессию
- **WHEN** препятствие останавливает текущий запуск
- **THEN** CLI сообщает его локально и не формирует уведомление о потребности в человеке

#### Scenario: Канал отсутствует перед новым поручением
- **GIVEN** активной собственной сессии нет, Git содержит работу, а `notifications.intervention` отсутствует
- **WHEN** production-команда проверяет входы нового поручения
- **THEN** CLI указывает отсутствующий путь, завершается с кодом `2` и не создаёт и не изменяет workspace или сессию

#### Scenario: Канал не требуется при отсутствии нового поручения
- **GIVEN** активной собственной сессии нет, Git чист, а `notifications.intervention` отсутствует
- **WHEN** production-команда проверяет актуальное состояние
- **THEN** CLI сообщает об отсутствии работы и завершается успешно, не считая отсутствие канала в сохранённом снимке препятствием

#### Scenario: Канал удалён во время существующего поручения
- **GIVEN** активная собственная сессия уже существует, а снимок текущего запуска не содержит `notifications.intervention`
- **WHEN** CLI восстанавливает сопровождение и сессии требуется участие человека
- **THEN** CLI локально показывает ошибку доставки, причину, ссылку и необходимость исправить конфигурацию и перезапустить CLI, сохраняет ту же сессию и продолжает наблюдение без нового агента

#### Scenario: Доверенный канал изменён после создания сессии
- **GIVEN** канал нового поручения получен из снимка запуска и сохранён до создания сессии, а затем файл конфигурации изменился
- **WHEN** той же сессии требуется участие человека в текущем процессе
- **THEN** CLI использует сохранённый канал без подмены и дополнительного подтверждения, а изменение файла может применить только новый процесс

#### Scenario: Исправление канала требует перезапуска
- **GIVEN** снимок текущего запуска не содержит корректного канала, а существующей собственной сессии требуется участие человека
- **WHEN** пользователь исправляет файл конфигурации без перезапуска CLI
- **THEN** CLI не перечитывает файл, продолжает наблюдать ту же сессию и сообщает, что для применения исправления требуется перезапуск

#### Scenario: Исправленный канал применяется после перезапуска
- **GIVEN** пользователь исправил канал после ошибки снимка, а собственная сессия остаётся активной и требует участия человека
- **WHEN** пользователь перезапускает CLI для того же change
- **THEN** новый процесс получает исправленный снимок, восстанавливает ту же сессию до возможного создания нового поручения и отправляет уведомление при сохраняющейся потребности

#### Scenario: Агент только начал работу
- **WHEN** CLI запустил автономное поручение и агент работает без затруднений
- **THEN** уведомление о готовности к участию пользователя не отправляется

#### Scenario: Повторный опрос ожидания человека
- **GIVEN** уведомление уже доставлено в текущем процессе и потребность в человеке не изменилась
- **WHEN** CLI снова читает состояние
- **THEN** CLI продолжает ожидание без нового уведомления

#### Scenario: Сбой после возможной доставки
- **GIVEN** ntfy мог принять запрос, но CLI остановлен до получения ответа
- **WHEN** после перезапуска участие человека всё ещё требуется
- **THEN** CLI повторно отправляет уведомление о той же сессии

#### Scenario: Сервис уведомлений не отвечает
- **WHEN** попытка уведомления завершается тайм-аутом
- **THEN** CLI показывает ошибку и ссылку локально, продолжает наблюдение и повторяет доставку с ограниченной частотой

#### Scenario: Сервис уведомлений отвечает перенаправлением
- **GIVEN** настроенный адрес ntfy отвечает перенаправлением на тот же или другой origin либо с HTTPS на HTTP
- **WHEN** адаптер отправляет авторизованное или неавторизованное уведомление
- **THEN** CLI считает доставку неподтверждённой, не выполняет запрос по адресу из `Location`, показывает ошибку локально и продолжает наблюдение

#### Scenario: Ntfy используется без токена
- **GIVEN** для канала `ntfy` настроен URL без `tokenEnv`
- **WHEN** CLI отправляет уведомление о потребности в человеке
- **THEN** адаптер выполняет запрос без заголовка авторизации и подтверждает доставку только по успешному ответу ntfy

#### Scenario: Ntfy показывает осмысленное действие открытия сессии
- **GIVEN** известной собственной сессии подготовки коммитов требуется участие человека
- **WHEN** адаптер ntfy отправляет уведомление
- **THEN** `Title` называет подготовку коммитов и change, текст объясняет причину без ID сессии и сырого deep-link, а единственное действие `Открыть сессию` имеет тип `view`, содержит проверенный Paseo deep-link этой сессии и `clear=true`, при этом `Click` отсутствует

#### Scenario: Открытие сессии очищает уведомление
- **GIVEN** клиент ntfy показывает уведомление известной собственной сессии
- **WHEN** пользователь активирует действие `Открыть сессию`
- **THEN** открывается точная текущая сессия Paseo, а уведомление отмечается прочитанным и убирается из панели независимо от поведения отдельного настойчивого звука клиента

#### Scenario: Для ntfy выбран приоритет
- **GIVEN** `notifications.intervention.priority` содержит `high`
- **WHEN** адаптер ntfy отправляет первоначальное или повторное уведомление в текущем процессе
- **THEN** каждый запрос передаёт `Priority: high`

#### Scenario: Приоритет ntfy не указан
- **GIVEN** `notifications.intervention.priority` отсутствует
- **WHEN** адаптер ntfy отправляет уведомление
- **THEN** запрос явно передаёт `Priority: default`

#### Scenario: Приоритет ntfy не поддерживается
- **GIVEN** `notifications.intervention.priority` содержит значение вне `min`, `low`, `default`, `high` и `max`
- **WHEN** CLI проверяет настройки уведомлений
- **THEN** CLI сообщает ошибку конфигурации с путём `notifications.intervention.priority` без молчаливого выбора другого значения

#### Scenario: Токен ntfy читается из окружения
- **GIVEN** `tokenEnv` называет непустую переменную окружения с токеном
- **WHEN** CLI отправляет уведомление о потребности в человеке
- **THEN** адаптер использует её значение как Bearer-токен, не раскрывая его в конфигурации, stdout или логах

#### Scenario: Переменная токена недоступна
- **GIVEN** `tokenEnv` задан, но соответствующая переменная отсутствует или пуста
- **WHEN** CLI пытается доставить уведомление
- **THEN** HTTP-запрос не выполняется, пользователь видит локальную ошибку и ссылку на известную сессию, а сопровождение продолжается

#### Scenario: Тип канала не поддерживается
- **GIVEN** конфигурация версии 1 содержит неизвестное значение `notifications.intervention.type`
- **WHEN** CLI проверяет настройки уведомлений
- **THEN** CLI сообщает точный путь и неподдерживаемое значение без молчаливого выбора ntfy

### Requirement: Наблюдаемый ход сопровождения

CLI MUST выводить в stdout по ходу работы русский человекочитаемый журнал: начало и результат проверок, обнаружение или создание workspace и своей сессии, восстановление, начало ожидания, периодическое подтверждение продолжающегося ожидания, проверку результата, закрытие, уведомления и препятствия. Порядок сообщений MUST сохранять хронологию текущего запуска и позволять человеку понять, что оркестратор уже сделал, что делает сейчас и чего ожидает. Сообщения MUST позволять связать действие с change и известной сессией и различать отсутствие работы, успешное поручение и ошибку.

Неизменные технические опросы MUST NOT засорять обычный вывод. Параметр `--verbose` MUST добавлять человекочитаемые результаты технических чтений и проверок, не скрывая сообщения обычного хода сопровождения. В рамках этого change CLI MUST предоставлять только человекочитаемый stdout; отдельный машиночитаемый формат и стабильная схема событий не входят в поведенческий контракт. Вывод MUST служить наблюдению и не являться источником восстановления или сохраняемой историей между запусками.

#### Scenario: Обычный вывод показывает ход поручения
- **GIVEN** пользователь запустил CLI без диагностической подробности
- **WHEN** оркестратор проверяет источники и сопровождает поручение
- **THEN** stdout в хронологическом порядке показывает завершённые переходы и текущее действие или ожидание без повторения неизменных технических чтений

#### Scenario: Включена диагностическая подробность
- **GIVEN** пользователь запустил CLI с параметром `--verbose`
- **WHEN** оркестратор выполняет техническое чтение или проверку
- **THEN** stdout остаётся человекочитаемым и дополняет обычный ход результатом этого действия

#### Scenario: Длительное ожидание агента
- **GIVEN** агент долго выполняет поручение без смены состояния
- **WHEN** CLI продолжает наблюдение
- **THEN** stdout периодически показывает, какую сессию и какое событие ожидает CLI, без повторения уведомлений

#### Scenario: Команда завершилась с препятствием
- **WHEN** актуальные данные не позволяют безопасно продолжить поручение
- **THEN** пользователь видит причину и доступный контекст для разбора, а завершившаяся команда возвращает ненулевой код
