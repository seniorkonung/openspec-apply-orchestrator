# OpenSpec Change Review: orchestrate-commit-preparation

## Assessment

**Format version:** 1
**Result:** No unresolved findings
**Coverage status:** Complete
**Summary:** Активных замечаний нет. Транспортная граница ntfy теперь однозначна для авторизованной и неавторизованной доставки: адаптер не следует HTTP-перенаправлениям, любой ответ `3xx` означает неподтверждённую доставку, а ограниченные повторы обращаются только к исходному адресу из неизменяемого снимка запуска. Сохраняются AR1 — параллельные поручения разных change, AR2 — возможный дубль в окне до видимости созданной сессии, AR3 — чистый Git не доказывает сохранение изменений и AR4 — доверенная репозиторная конфигурация выбирает адрес и переменную отдельного токена уведомлений.
**Validation:** `openspec validate orchestrate-commit-preparation --strict --no-interactive` завершился с кодом 0; `openspec instructions apply --change orchestrate-commit-preparation --json` подтвердил непрерывный ledger Phase 1–3, прогресс 33/46 и 13 невыполненных задач только в Phase 3. Валидатор формата review и `git diff --check` завершились с кодом 0. Go MCP в сессии недоступен; структура, API и ссылки исследованы командами `go list`, `go doc` и `rg`. Go-тесты не запускались, поскольку код не изменялся и предметом был аудит плановых артефактов; реальная доставка ntfy и открытие ссылки на пользовательском устройстве остаются будущими доказательствами задач 3.9–3.12.

## Accepted risks

### AR1 · Между поручениями разных change нет автоматического взаимного исключения

- **Evidence:** [Proposal](proposal.md) ограничивает последовательность выбранным change и оставляет изоляцию параллельных change пользователю. [Спецификация сессий](specs/managed-paseo-sessions/spec.md) требует не считать собственную сессию другого change препятствием. [Design](design.md), разделы 4 и Risks / Trade-offs, ограничивает lock выбранным change; задачи 2.2, 2.6 и 2.8 применяют состояние Git только к текущей команде и не добавляют координацию разных change.
- **Potential impact:** Два поручения разных change могут одновременно изменить один рабочий каталог, индекс, ветку или связанные Git-ссылки. Один агент может включить в свои коммиты изменения другого поручения либо помешать его работе.
- **Acceptance rationale:** Пользователь явно решил не вводить глобальную защиту: оркестратор не может надёжно определить конфликт по каталогам, путям и характеру действий, а запрет всех параллельных change исключил бы полезную независимую работу.
- **Scope and assumptions:** Риск относится к параллельным поручениям разных change, включая один Git-репозиторий и связанные worktree. Для одного выбранного change сохраняются блокировка второго CLI, продолжение видимой активной собственной сессии и обнаружение нескольких таких сессий. Пользователь отвечает за ветки, worktree, каталоги и последовательность разных change.
- **Reopen when:** Оркестратор начнёт автоматически управлять несколькими change как единым workflow, пообещает репозиторное взаимное исключение или получит обязательную машиночитаемую модель конфликтов и изоляции.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07: глобальную защиту не вводить, параллельность разных change оставить под контролем человека.
- **Originating finding:** F2
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Последовательность собственных поручений выбранного change»; [Design](design.md), разделы Goals / Non-Goals, 4 и Risks / Trade-offs.

### AR2 · Повторный ручной запуск может продублировать ещё не видимую созданную сессию

- **Evidence:** [Design](design.md), раздел 5, выбирает один `paseo run --background --json` без предварительного резервирования и сохраняет окно между принятием команды daemon и видимостью сессии. [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления», разрешает новой явной команде создать сессию, если активная собственная сессия не видна и Git грязный. Задачи 2.6 и 2.8 сохраняют эту модель.
- **Potential impact:** При аварии в узком окне и слишком раннем повторном запуске могут появиться две собственные сессии одного change. Они способны конкурирующе менять Git; после появления обеих CLI остановится на неоднозначности и потребует ручного закрытия лишней сессии.
- **Acceptance rationale:** Пользователь считает окно пренебрежимо малым для CLI, который запускается только вручную после осмотра состояния Paseo и репозитория. Предварительное резервирование добавило бы несоразмерное постоянное состояние и тупиковый выход без сессии.
- **Scope and assumptions:** CLI запускается одним пользователем вручную; текущий процесс не повторяет неопределённое создание автоматически; после его аварии пользователь проверяет Paseo перед новым запуском. Риск не распространяется на обещание автоматической дедупликации.
- **Reopen when:** Появятся автоматические перезапуски, фоновые повторы, запуск через вышестоящий оркестратор, несколько независимых владельцев или требование гарантировать отсутствие дублирующих сессий.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 не усложнять систему ради этого окна; итоговый пакет прямого создания и восстановления видимой сессии подтверждён отдельно.
- **Originating finding:** F3
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0003](../../../docs/adr/0003-identify-managed-session-after-direct-dispatch.md); [Design](design.md), раздел 5; [спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления».

### AR3 · Чистый Git не доказывает, что исходные изменения сохранены в коммитах

- **Evidence:** [Спецификация подготовки коммитов](specs/commit-preparation/spec.md), требование «Проверяемое завершение подготовки коммитов», делает свежую чистоту Git единственным критерием CLI и передаёт содержательную ответственность агенту и пользователю. [Design](design.md), раздел 6, отказывается от неизменяемого снимка и проверки диапазона коммитов. Задачи 2.3, 2.6 и 2.8 намеренно проверяют prompt и итоговый Git без структурированного результата.
- **Potential impact:** Агент может получить чистое дерево через удаление, reset, stash или иной способ, не сохранив все изменения в требуемых коммитах, а CLI сообщит операционный успех.
- **Acceptance rationale:** Пользователь определил создание и проверку содержательных коммитов как полную ответственность агента, а при затруднении — агента вместе с человеком. Оркестратор должен только решить, нужна ли сессия, и после её работы проверить отсутствие незакоммиченных изменений.
- **Scope and assumptions:** Риск относится к команде подготовки коммитов и доверенному локальному агенту. Встроенный prompt запрещает отбрасывать изменения и обходить правила репозитория, но CLI не обещает доказательство сохранности содержимого.
- **Reopen when:** Агент станет недоверенным, появится требование защищать пользователя от ошибочных или разрушительных Git-действий либо критерий успеха будет расширен до доказанного сохранения исходного содержимого.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 передать анализ и создание коммитов агенту целиком; согласованная упрощённая модель без исходного снимка и структурированного результата подтверждена отдельно.
- **Originating finding:** F5
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0001](../../../docs/adr/0001-recover-from-paseo-and-workflow-results.md); [спецификация подготовки коммитов](specs/commit-preparation/spec.md), требование «Проверяемое завершение подготовки коммитов»; [Design](design.md), раздел 6.

### AR4 · Доверенная конфигурация репозитория выбирает адрес доставки и переменную токена

- **Evidence:** [Proposal](proposal.md) и [спецификация уведомлений](specs/intervention-reporting/spec.md), требование «Доставка уведомлений через настроенный канал», относят `openspec-apply-orchestrator.json`, включая полученные из Git и выполненные full-access агентом изменения, к доверенной пользовательской политике. [Design](design.md), разделы 2 и Risks / Trade-offs, сохраняет выбор пары `url`/`tokenEnv` без отдельного подтверждения или trust store и фиксирует один неизменяемый снимок на запуск; исправленную конфигурацию применяет новый процесс после восстановления той же сессии. Задачи 3.1, 3.3, 3.6, 3.10 и 3.11 протягивают эту границу в реализацию, проверки и руководство.
- **Potential impact:** Доверенное изменение конфигурации способно направить значение выбранной переменной окружения и контекст сессии на выбранный адрес; раскрытие topic или выделенного токена может позволить нежелательную публикацию и потребовать пересоздания канала.
- **Acceptance rationale:** Пользователь считает целенаправленную подмену принадлежащего ему репозитория или происхождения его Git-изменений менее вероятной, чем компрометацию операционной системы, уже находящуюся вне полезной защиты этого механизма. Уведомление и ссылка на локальную Paseo-сессию не содержат значимых конфиденциальных данных, а раскрытие отдельного токена уведомлений не причиняет финансового или иного существенного ущерба кроме спама и замены канала. Дополнительное подтверждение либо вынесенный trust store поэтому не оправдывают усложнения личного workflow.
- **Scope and assumptions:** Риск принят только для личной Linux-local среды, доверенного пользовательского репозитория и его Git-изменений, локального full-access агента и отдельного заменяемого токена, не имеющего значимых полномочий вне канала уведомлений. Полный адрес topic и токен по-прежнему скрываются из stdout и диагностики.
- **Reopen when:** CLI начнёт работать с недоверенными репозиториями, ветками или участниками, запускаться внешней автоматизацией либо в многопользовательской среде; агент перестанет входить в доверенную границу; уведомление или ссылка станут содержать чувствительные данные; выбранный токен получит значимые полномочия или последствия его раскрытия перестанут ограничиваться спамом и пересозданием канала.
- **Acceptance authority:** Явное решение пользователя от 2026-09-09 сохранить репозиторную конфигурацию доверенной политикой и принять ограниченные последствия раскрытия выделенного токена уведомлений.
- **Originating finding:** F13
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [Proposal](proposal.md), описание схемы уведомлений; [спецификация уведомлений](specs/intervention-reporting/spec.md), требование «Доставка уведомлений через настроенный канал»; [Design](design.md), разделы 2 и Risks / Trade-offs.

## Review coverage

Проведён широкий повторный аудит фактического графа `proposal → specs → design → adr → plan → tasks` с углублением во все 13 задач Phase 3 и их переход от завершённой Phase 2. Полностью прочитаны метаданные и схема `intent-driven` версии 5, все артефакты change, текущие `review.md` и `implementation-review.md`, `CONTEXT.md`, связанные обсуждения, индекс ADR и три принадлежащих change ADR. Основных спецификаций пока нет. Ledger образует непрерывный префикс Phase 1–3; Phase 1 и Phase 2 представлены только выполненными задачами, а Phase 3 — единственный открытый пакет.

Обязательства Phase 3 прослежены от proposal и capability `intervention-reporting` через требования доставки, длительного сопровождения и наблюдаемого stdout, решения design, outcome/readiness Phase 3 и задачи 3.1–3.13. В реальном коде проверены текущие границы `internal/config`, `internal/orchestrator`, `internal/paseo` и production-команды, а также существующие тестовые seams, process harness и точки будущего подключения `internal/notify`. В глубину проверены публичный CLI-контракт, единый снимок конфигурации и независимое использование его типизированных разделов, применение исправлений после перезапуска, секреты и trust boundary, HTTP/ntfy, запрет redirect для запросов с токеном и без него, типизация события и ссылки, повторные попытки, отмена, idle polling, возобновление `wait`, закрытие сессии, свежесть Git/Paseo/OpenSpec, redaction, обычный и подробный человекочитаемый stdout, интеграционные отказные пути, документация и ручная приёмка на устройстве.

[Официальная документация Go `net/http`](https://pkg.go.dev/net/http) подтверждает, что клиент по умолчанию следует перенаправлениям, а `307` и `308` сохраняют метод и тело POST. [Официальная документация ntfy](https://docs.ntfy.sh/publish/) подтверждает прямую POST-публикацию, Bearer-аутентификацию, произвольный URI в `Click` и чувствительность topic URL. Текущий контракт запрещает второй запрос по `Location` для любого `3xx`; design сохраняет ту же политику, задача 3.3 доказывает её для авторизованных и неавторизованных same-origin, cross-origin и HTTPS→HTTP случаев, а задача 3.10 проверяет продолжение сопровождения и повторы только к исходному адресу. Эти свойства согласованы с принятой личной доверенной границей AR4 и единым снимком конфигурации. AR1–AR3 перепроверены по актуальным спецификациям, design, ADR и всем трём фазам; условия их принятия не изменились.
