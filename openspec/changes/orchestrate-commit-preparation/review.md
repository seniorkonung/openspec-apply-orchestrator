# OpenSpec Change Review: orchestrate-commit-preparation

## Assessment

**Format version:** 1
**Result:** No unresolved findings
**Coverage status:** Complete
**Summary:** Артефакты задают один замкнутый жизненный цикл через штатный Paseo CLI: оркестратор находит только активный workspace, связывает собственную сессию с его полным ID через метки, продолжает видимую активную сессию и архивирует её после проверяемого завершения. Архивированные workspace не перечисляются, а архивированные сессии остаются историей и не участвуют в восстановлении. Подтверждена граница Linux, локального daemon того же пользователя и локальных файловых систем; прямой протокол и WebSocket-клиент исключены. Принятые риски: AR1 — параллельные поручения разных change, AR2 — возможный дубль в окне до видимости созданной сессии, AR3 — чистый Git не доказывает сохранение изменений.
**Validation:** После согласования артефактов `openspec validate orchestrate-commit-preparation --strict --no-interactive`, `go test ./...` и `go vet ./...` завершились с кодом 0. В коде реализована только задача 1.1 с типизированным наблюдением сессии; адаптер Paseo CLI, связь `oa.workspace` и интеграционные испытания ещё являются запланированной работой. Контракт команд проверен по справке, установленному коду и безопасным операциям чтения Paseo CLI 0.7.2; живые испытания создания, восстановления, архивирования, доставки ntfy и открытия ссылки предусмотрены задачами и не считаются уже доказанными свойствами.

## Accepted risks

### AR1 · Между поручениями разных change нет автоматического взаимного исключения

- **Evidence:** [Proposal](proposal.md) ограничивает последовательность выбранным change и оставляет изоляцию параллельных change пользователю. [Спецификация сессий](specs/managed-paseo-sessions/spec.md) требует не считать собственную сессию другого change препятствием. [Design](design.md), разделы 4 и Risks / Trade-offs, ограничивает lock выбранным change; [задачи](tasks.md) 1.3, 1.5–1.8 проверяют эту границу.
- **Potential impact:** Два поручения разных change могут одновременно изменить один рабочий каталог, индекс, ветку или связанные Git-ссылки. Один агент может включить в свои коммиты изменения другого поручения либо помешать его работе.
- **Acceptance rationale:** Пользователь явно решил не вводить глобальную защиту: оркестратор не может надёжно определить конфликт по каталогам, путям и характеру действий, а запрет всех параллельных change исключил бы полезную независимую работу.
- **Scope and assumptions:** Риск относится к параллельным поручениям разных change, включая один Git-репозиторий и связанные worktree. Для одного выбранного change сохраняются блокировка второго CLI, продолжение видимой активной собственной сессии и обнаружение нескольких таких сессий. Пользователь отвечает за ветки, worktree, каталоги и последовательность разных change.
- **Reopen when:** Оркестратор начнёт автоматически управлять несколькими change как единым workflow, пообещает репозиторное взаимное исключение или получит обязательную машиночитаемую модель конфликтов и изоляции.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07: глобальную защиту не вводить, параллельность разных change оставить под контролем человека.
- **Originating finding:** F2
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Последовательность собственных поручений выбранного change»; [Design](design.md), разделы Goals / Non-Goals, 4 и Risks / Trade-offs.

### AR2 · Повторный ручной запуск может продублировать ещё не видимую созданную сессию

- **Evidence:** [Design](design.md), раздел 5, выбирает один `paseo run --background --json` без предварительного резервирования и сохраняет окно между принятием команды daemon и видимостью сессии. [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления», разрешает новой явной команде создать сессию, если активная собственная сессия не видна и Git грязный. [ADR 0003](../../../docs/adr/0003-identify-managed-session-after-direct-dispatch.md) фиксирует ту же границу.
- **Potential impact:** При аварии в узком окне и слишком раннем повторном запуске могут появиться две собственные сессии одного change. Они способны конкурирующе менять Git; после появления обеих CLI остановится на неоднозначности и потребует ручного закрытия лишней сессии.
- **Acceptance rationale:** Пользователь считает окно пренебрежимо малым для CLI, который запускается только вручную после осмотра состояния Paseo и репозитория. Предварительное резервирование добавило бы несоразмерное постоянное состояние и тупиковый выход без сессии.
- **Scope and assumptions:** CLI запускается одним пользователем вручную; текущий процесс не повторяет неопределённое создание автоматически; после его аварии пользователь проверяет Paseo перед новым запуском. Риск не распространяется на обещание автоматической дедупликации.
- **Reopen when:** Появятся автоматические перезапуски, фоновые повторы, запуск через вышестоящий оркестратор, несколько независимых владельцев или требование гарантировать отсутствие дублирующих сессий.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 не усложнять систему ради этого окна; итоговый пакет прямого создания и восстановления видимой сессии подтверждён отдельно.
- **Originating finding:** F3
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0003](../../../docs/adr/0003-identify-managed-session-after-direct-dispatch.md); [Design](design.md), раздел 5; [спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления».

### AR3 · Чистый Git не доказывает, что исходные изменения сохранены в коммитах

- **Evidence:** [Спецификация подготовки коммитов](specs/commit-preparation/spec.md), строки 55–62, делает свежую чистоту Git единственным критерием CLI и передаёт содержательную ответственность агенту и пользователю. [Design](design.md), строки 98–117, отказывается от неизменяемого снимка и проверки диапазона коммитов. [ADR 0001](../../../docs/adr/0001-recover-from-paseo-and-workflow-results.md) закрепляет эту границу результата.
- **Potential impact:** Агент может получить чистое дерево через удаление, reset, stash или иной способ, не сохранив все изменения в требуемых коммитах, а CLI сообщит операционный успех.
- **Acceptance rationale:** Пользователь определил создание и проверку содержательных коммитов как полную ответственность агента, а при затруднении — агента вместе с человеком. Оркестратор должен только решить, нужна ли сессия, и после её работы проверить отсутствие незакоммиченных изменений.
- **Scope and assumptions:** Риск относится к команде подготовки коммитов и доверенному локальному агенту. Встроенный промпт запрещает отбрасывать изменения и обходить правила репозитория, но CLI не обещает доказательство сохранности содержимого.
- **Reopen when:** Агент станет недоверенным, появится требование защищать пользователя от ошибочных или разрушительных Git-действий либо критерий успеха будет расширен до доказанного сохранения исходного содержимого.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 передать анализ и создание коммитов агенту целиком; согласованная упрощённая модель без исходного снимка и структурированного результата подтверждена отдельно.
- **Originating finding:** F5
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0001](../../../docs/adr/0001-recover-from-paseo-and-workflow-results.md); [спецификация подготовки коммитов](specs/commit-preparation/spec.md), требование «Проверяемое завершение подготовки коммитов»; [Design](design.md), раздел 6.

## Review coverage

Проверка выполнена 2026-09-07 по текущим файлам рабочего дерева. Прочитаны `AGENTS.md`, `CONTEXT.md`, согласованные ограничения продукта и граница первого change, `openspec/config.yaml`, метаданные change и фактическая схема `intent-driven` версии 5. Проверен граф `proposal → specs → design → adr → plan → tasks`, включая все три delta spec, манифест, индекс ADR и три принадлежащих change ADR со статусом `proposed`. Основных спецификаций пока нет; из прикладного кода проверены Go-модуль и реализация завершённой задачи 1.1.

Проверены соответствие возможностей proposal путям спецификаций, один явный запуск подготовки коммитов, отсутствие работы, создание одной командой с первоначальным промптом и метками агента, принадлежность активного workspace и сессий, продолжение видимой активной сессии, поведение работающего и остановившегося агента, архивирование, ручная помощь и закрытие при чистом и грязном Git. Контракт имеет выход из каждой наблюдаемой ветви: продолжение той же активной сессии, успех, неуспех текущего запуска или разрешение новой попытки в следующем явном запуске. Проверены настройки, защита секретов, ограниченные повторы чтения и уведомлений, stdout, сигналы, установка и откат.

Отдельно прослежены принятые границы: отсутствие координации разных change (AR1), окно прямого создания до видимости сессии (AR2) и доверие содержательной работе агента при критерии чистого Git (AR3). Proposal, спецификации, design, ADR 0002, plan и задачи согласованно ограничивают поставку Linux, локальным daemon Paseo того же пользователя и локальными файловыми системами; неподдерживаемая среда отклоняется до мутаций, а пользовательское устройство ntfy проверяется отдельно.

Поверхность Paseo 0.7.2 проверена по `run`, `workspace ls`, `ls`, `inspect`, `archive`, `status` и их JSON: активные workspace перечисляются CLI, фильтры меток применяются до ограничения списка сессий, `inspect` уточняет кандидата, а `status` сообщает локальность, владельца, `serverId` и версии. Архивированные workspace не нужны, а для классификации собственных активных сессий достаточно различить `0 / 1 / больше одной` после серверного фильтра; интеграционные испытания Phase 1 остаются обязательной работой.

План содержит три строго последовательных результата. В `tasks.md` представлен только незавершённый пакет Phase 1, что соответствует схеме; выполненная задача 1.1 сохранена, а задачи 1.2–1.8 покрывают безопасный процессный адаптер Paseo CLI, активный workspace, широкую и точную фильтрацию с `oa.workspace`, создание и архивирование, Linux-local владение, продолжение и интеграционную проверку. Пакеты Phase 2 и Phase 3 должны создаваться последовательно после завершения предыдущей фазы.
