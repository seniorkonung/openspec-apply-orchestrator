# OpenSpec Change Review: orchestrate-commit-preparation

## Assessment

**Format version:** 1
**Result:** No unresolved findings
**Coverage status:** Complete
**Summary:** После согласованного разрешения F11 активных замечаний не осталось. Артефакты теперь требуют `notifications.intervention` до создания нового production-поручения и отличают этот отказ от восстановления уже существующей активной собственной сессии при отсутствующем текущем канале. Принятые риски сохраняются: AR1 — параллельные поручения разных change, AR2 — возможный дубль в окне до видимости созданной сессии, AR3 — чистый Git не доказывает сохранение изменений.

## Accepted risks

### AR1 · Между поручениями разных change нет автоматического взаимного исключения

- **Evidence:** [Proposal](proposal.md) ограничивает последовательность выбранным change и оставляет изоляцию параллельных change пользователю. [Спецификация сессий](specs/managed-paseo-sessions/spec.md) требует не считать собственную сессию другого change препятствием. [Design](design.md), разделы 4 и Risks / Trade-offs, ограничивает lock выбранным change; задачи 2.2, 2.6 и 2.8 применяют состояние Git только к текущей команде и не добавляют координацию разных change.
- **Potential impact:** Два поручения разных change могут одновременно изменить один рабочий каталог, индекс, ветку или связанные Git-ссылки. Один агент может включить в свои коммиты изменения другого поручения либо помешать его работе.
- **Acceptance rationale:** Пользователь явно решил не вводить глобальную защиту: оркестратор не может надёжно определить конфликт по каталогам, путям и характеру действий, а запрет всех параллельных change исключил бы полезную независимую работу.
- **Scope and assumptions:** Риск относится к параллельным поручениям разных change, включая один Git-репозиторий и связанные worktree. Для одного выбранного change сохраняются блокировка второго CLI, продолжение видимой активной собственной сессии и обнаружение нескольких таких сессий. Пользователь отвечает за ветки, worktree, каталоги и последовательность разных change.
- **Reopen when:** Оркестратор начнёт автоматически управлять несколькими change как единым workflow, пообещает репозиторное взаимное исключение или получит обязательную машиночитаемую модель конфликтов и изоляции.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07: глобальную защиту не вводить, параллельность разных change оставить под контролем человека.
- **Originating finding:** F2
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Последовательность собственных поручений выбранного change»; [Design](design.md), разделы Goals / Non-Goals, 4 и Risks / Trade-offs.

### AR2 · Повторный ручной запуск может продублировать ещё не видимую созданную сессию

- **Evidence:** [Design](design.md), раздел 5, выбирает один `paseo run --background --json` без предварительного резервирования и сохраняет окно между принятием команды daemon и видимостью сессии. [Спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления», разрешает новой явной команде создать сессию, если активная собственная сессия не видна и Git грязный. Задачи 2.6 и 2.8 сохраняют эту модель.
- **Potential impact:** При аварии в узком окне и слишком раннем повторном запуске могут появиться две собственные сессии одного change. Они способны конкурирующе менять Git; после появления обеих CLI остановится на неоднозначности и потребует ручного закрытия лишней сессии.
- **Acceptance rationale:** Пользователь считает окно пренебрежимо малым для CLI, который запускается только вручную после осмотра состояния Paseo и репозитория. Предварительное резервирование добавило бы несоразмерное постоянное состояние и тупиковый выход без сессии.
- **Scope and assumptions:** CLI запускается одним пользователем вручную; текущий процесс не повторяет неопределённое создание автоматически; после его аварии пользователь проверяет Paseo перед новым запуском. Риск не распространяется на обещание автоматической дедупликации.
- **Reopen when:** Появятся автоматические перезапуски, фоновые повторы, запуск через вышестоящий оркестратор, несколько независимых владельцев или требование гарантировать отсутствие дублирующих сессий.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 не усложнять систему ради этого окна; итоговый пакет прямого создания и восстановления видимой сессии подтверждён отдельно.
- **Originating finding:** F3
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0003](../../../docs/adr/0003-identify-managed-session-after-direct-dispatch.md); [Design](design.md), раздел 5; [спецификация сессий](specs/managed-paseo-sessions/spec.md), требование «Прямая отправка через Paseo CLI и граница восстановления».

### AR3 · Чистый Git не доказывает, что исходные изменения сохранены в коммитах

- **Evidence:** [Спецификация подготовки коммитов](specs/commit-preparation/spec.md), требование «Проверяемое завершение подготовки коммитов», делает свежую чистоту Git единственным критерием CLI и передаёт содержательную ответственность агенту и пользователю. [Design](design.md), раздел 6, отказывается от неизменяемого снимка и проверки диапазона коммитов. Задачи 2.3, 2.6 и 2.8 намеренно проверяют prompt и итоговый Git без структурированного результата.
- **Potential impact:** Агент может получить чистое дерево через удаление, reset, stash или иной способ, не сохранив все изменения в требуемых коммитах, а CLI сообщит операционный успех.
- **Acceptance rationale:** Пользователь определил создание и проверку содержательных коммитов как полную ответственность агента, а при затруднении — агента вместе с человеком. Оркестратор должен только решить, нужна ли сессия, и после её работы проверить отсутствие незакоммиченных изменений.
- **Scope and assumptions:** Риск относится к команде подготовки коммитов и доверенному локальному агенту. Встроенный prompt запрещает отбрасывать изменения и обходить правила репозитория, но CLI не обещает доказательство сохранности содержимого.
- **Reopen when:** Агент станет недоверенным, появится требование защищать пользователя от ошибочных или разрушительных Git-действий либо критерий успеха будет расширен до доказанного сохранения исходного содержимого.
- **Acceptance authority:** Явное решение пользователя от 2026-09-07 передать анализ и создание коммитов агенту целиком; согласованная упрощённая модель без исходного снимка и структурированного результата подтверждена отдельно.
- **Originating finding:** F5
- **Acceptance lifetime:** Change-scoped
- **Decision record:** [ADR 0001](../../../docs/adr/0001-recover-from-paseo-and-workflow-results.md); [спецификация подготовки коммитов](specs/commit-preparation/spec.md), требование «Проверяемое завершение подготовки коммитов»; [Design](design.md), раздел 6.

## Review coverage

Широкий аудит повторён после изменения плановых артефактов в коммите `cd1b95d`; после согласованного решения отдельно перепроверены исправление F11 и его влияние на текущую и следующую фазы. Полностью прочитаны фактический граф `proposal → specs → design → adr → plan → tasks`, метаданные и схема `intent-driven` версии 5, текущий review, `CONTEXT.md`, связанные обсуждения, индекс ADR и все три принадлежащих change ADR. Основных спецификаций ещё нет. Ledger представляет непрерывный префикс Phase 1–2; Phase 1 завершена, а восемь задач 2.13, 2.14, 2.5, 2.6, 2.10, 2.7, 2.8 и 2.9 образуют единственный незавершённый пакет. Phase 3 закономерно ещё не представлена задачами и не считалась частью текущего пакета.

Прослежены блокирующее ожидание `paseo wait`, сохранение известного ID, обязательное свежее наблюдение после сигнала, чистый и грязный Git, условное чтение настроек новой сессии, локальная передача потребности в человеке, ошибки источников, отмена, коды выхода, production-сборка и daemon-backed приёмка. Задачи образуют исполнимый порядок: 2.13 и 2.14 независимо подготавливают границы, 2.5–2.6 строят цикл, 2.10 замыкает ошибки, 2.7 собирает команду, 2.8 проверяет реальные границы, 2.9 служит checkpoint. Намеренное завершение Phase 2 после локальной передачи человеку согласуется с plan; длительное ожидание человека, доставка ntfy и ручное закрытие остаются Phase 3.

Углублённо проверены архитектура и публичная CLI/JSON-конфигурация, внешние процессы Paseo/OpenSpec/Git, типизация состояний, конкурентное владение, восстановление, свежесть источников, безопасность мутаций и вывода, наблюдаемость и интеграционная топология. Из кода проверены API и реализации `internal/orchestrator`, `internal/paseo`, `internal/config`, `internal/ownership`, процессные drivers и изолированный Paseo-стенд. OpenSpec 1.12.0 подтвердил граф и прогресс 14/22; Paseo 0.7.2 и его установленный код подтвердили контракт `wait` и необходимость отбрасывать `message`. Актуальная публичная документация подтверждает блокирующее назначение `paseo wait`; документация ntfy подтверждает `Click` и Bearer-аутентификацию, но эти HTTP-обязательства относятся к Phase 3. Повторно проверены AR1–AR3; их условия и границы остаются применимыми.

F11 закрыт согласованной сквозной семантикой. Спецификация требует канал до создания нового поручения, возвращает код `2` и запрещает мутации при его отсутствии, но не читает конфигурацию при чистом Git без работы. Уже существующая активная собственная сессия восстанавливается без текущего канала; возникшая потребность в человеке остаётся локально видимой ошибкой доставки со ссылкой и не приводит к замене либо прекращению сопровождения. Design отделяет типизированные входы создания от ленивого разрешения канала при восстановлении, plan проводит эту границу через Phase 2 и Phase 3, а задачи 2.14, 2.7, 2.8 и 2.9 покрывают модульное, production и daemon-backed доказательство обоих исходов. Для остальных обязательств невыполненного пакета активных разрывов не найдено. Последовательные `-p=1 -count=1` gates 2.8 и 2.9 соответствуют изолированной daemon-backed топологии, а модульные проверки покрывают неподдерживаемые статусы, несовпавший ID, отмену и отсутствие технического polling.
