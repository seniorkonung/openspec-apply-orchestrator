Исходного кода и тестов нет. ## Goals / Non-Goals

**Goals:**

- Сопровождать одно поручение коммитов выбранного change, продолжать видимую активную сессию после остановки процесса и завершать команду по свежему состоянию Git.
- Различать собственную сессию, сессию пользователя, работу агента, потребность в человеке и закрытие.
- Оставить механизм сопровождения пригодным для следующих типов сессий без реализации их workflow сейчас.

**Non-Goals:**

- Обсуждение задач, Apply, ревью, планирование фаз, push и архивирование change.
- Собственная база или журнал прогресса, предварительное резервирование будущего агента, неизменяемый снимок порученных файлов или структурированный отчёт агента о коммитах.
- Проверка того, что чистое дерево достигнуто именно сохранением всех исходных изменений, автоматическое разрешение конфликтов и исправление кода.
- Координация поручений разных change и определение безопасности их параллельной работы по веткам, worktree, затронутым путям или текущим действиям.

Граница поставки, предложенная для этого change: Linux, локальные CLI и daemon Paseo одного пользователя, один общий рабочий каталог. Удалённый daemon, сетевые файловые системы и распределённая координация потребуют отдельного решения. Это допущение проектирования, а не подтверждённое в исходном обсуждении требование. Go выбран по существующему набору инструментов; конкретные модели в программу не зашиваются.

## Decisions

### 1. Узкое ядро сопровождения и адаптеры

Предлагается Go-модуль `github.com/seniorkonung/openspec-apply-orchestrator`. Ядро преобразует проверенный снимок источников в одно действие. Адаптеры выполняют чтение и воздействие; содержательные решения принадлежат агенту и участвующему пользователю. Карта ответственности достаточно мала для таблицы; отдельная C4-диаграмма здесь не добавляет границ.

| Часть | Ответственность |
|---|---|
| `cmd/openspec-apply-orchestrator` | Аргументы, сигналы, stdout и код завершения. |
| `internal/orchestrator` | Типы наблюдаемого состояния, классификация, выбор одного действия и повторное чтение. |
| `internal/paseo` | Локальный транспорт, проверка протокола, workspace, метки собственных сессий, создание и архивирование. |
| `internal/gitstate`, `internal/openspec` | Чистота Git и разрешение активного change через OpenSpec CLI. |
| `internal/config`, `internal/prompts` | Проверенные настройки и встроенные версионированные поручения. |
| `internal/notify`, `internal/ownership` | HTTP-уведомления и исключение второго процесса. |

Это предлагаемые новые пути, а не найденные модули. Интерфейсы принадлежат потребляющему ядру; общий движок всех последующих change и реестр плагинов не создаются. Внешний JSON валидируется на границе и преобразуется во взаимоисключающие варианты наблюдения: собственной активной сессии нет, одна сессия работает, одна сессия ожидает действия, сессия закрыта в текущем наблюдении либо состояние неоднозначно. Специальные варианты `completed` и `needs_help` из текста ответа агента не вводятся.

Альтернатива — shell-сценарий поверх текстового вывода Paseo. Он проще в начале, но не даёт полной и проверяемой принадлежности сессий. TypeScript SDK устраняет часть транспортной работы, но вводит другой основной runtime; Go-адаптер ограничивается необходимой частью протокола и проверяется на совместимость.

### 2. Контракт запуска и конфигурация

Команда: `openspec-apply-orchestrator prepare-commits --change <name>`, с необязательным `--store <id>`. OpenSpec определяет planning home; при явном store все обращения сохраняют этот scope. Код и настройки берутся из канонического рабочего Git-каталога запуска. Планирование во внешнем store допустимо как контекст; поручение коммитов относится только к выбранному рабочему Git-каталогу и не коммитит несколько репозиториев одновременно.

Конфигурация — `openspec-apply-orchestrator.json` в корне рабочего дерева. JSON выбран для строгой проверки без дополнительного парсера. Предлагаемые поля:

| Поле | Контракт |
|---|---|
| `version` | Версия формата, для этого контракта `1`. |
| `sessions.commit-preparation.provider`, `.model` | Обязательные непустые значения без встроенной модели по умолчанию. |
| `.reasoning`, `.mode` | Необязательные точные значения, отображаемые в `thinkingOptionId` и `modeId`. |
| `.providerOptions` | Необязательный объект параметров провайдера, проверяемый по его объявленному контракту. |
| `paseo.endpoint` | Явный локальный Unix socket; адрес удалённого daemon отклоняется. `serverId` читается из ответа сервера. |
| `ntfy.url`, `ntfy.tokenEnv` | Полный URL публикации и необязательное имя переменной окружения с токеном. Секрет не записывается в файл конфигурации. |

Неизвестные поля отклоняются с указанием пути. Значения не проходят через shell. При продолжении настройки существующего агента сохраняют силу; новые настройки применяются к следующей новой сессии. Перезапуск не пересоздаёт видимого активного агента ради смены модели.

Git и OpenSpec вызываются через `exec.CommandContext` со списком аргументов. Для Git включается `GIT_OPTIONAL_LOCKS=0`; CLI не выполняет `add`, `commit`, `reset`, `stash`, `write-tree` и не записывает служебные объекты. Запросы ограничены сроком и объёмом ответа. Ошибка JSON, неполная выборка или несогласованные корни возвращают препятствие, а не пустой список.

### 3. Прямой адаптер Paseo с проверяемой совместимостью

Адаптер подключается по WebSocket через локальный Unix socket, проходит `hello` и проверяет версию протокола и сведения сервера. Единственная добавочная транспортная библиотека — Go WebSocket-клиент с поддержкой собственного dialer, выбранный и закреплённый при реализации транспортного контракта.

Необходимая поверхность адаптера: полное постраничное чтение workspace и агентов, включая метки и `archivedAt`; создание агента с конфигурацией, `initialPrompt` и метками в одном запросе; наблюдение состояния, запросов разрешения и ошибок; архивирование. Встроенная очередь не переотправляет мутации после reconnect. Для решения команды не требуется разбирать текст разговора или восстанавливать специальный JSON-результат из истории.

Адаптер не читает приватные файлы хранилища daemon. Извлечение сведений регулярным выражением из человекочитаемого вывода отклонено. Неполная выборка агентов, неподдерживаемая версия и недоступный источник являются препятствием, а не доказательством отсутствия активной сессии.

### 4. Идентичность, принадлежность и исключение конкуренции

Ключ change вычисляется из канонических путей рабочего дерева и planning home, имени change и `serverId`. Git remote не является идентичностью: две рабочие копии одного remote различаются. Символические ссылки нормализуются.

Workspace получает версионированные признаки владельца и ключ change без состояния поручения. Рабочий агент создаётся с метками `oa.owner`, `oa.version`, `oa.change`, `oa.kind`; проверяются также настоящий `workspaceId`, cwd и отсутствие чужого родителя. Человекочитаемый title агента не определяет принадлежность. Пользовательские сессии не получают этот полный набор меток и не участвуют в выборе действия. Повреждённые признаки и несколько активных собственных сессий создают неоднозначность.

Локальный экземпляр держит неблокирующий advisory lock на открытом существующем корне выбранного change, без создания lock-файла и записи PID. Это сериализует экземпляры CLI одного change. Разные change используют разные lock и могут сопровождаться параллельно, даже если относятся к одному Git common dir или связанным worktree. Безопасную изоляцию и последовательность таких поручений определяет пользователь.

### 5. Прямое создание без предварительного резервирования

Когда активной собственной сессии нет, а Git грязный, CLI после свежего полного чтения Paseo отправляет один `create_agent_request`. Запрос одновременно содержит конфигурацию агента, встроенный первоначальный промпт и метки происхождения. Отдельного `requestKey`, записи `reserved/finalized` и изменения workspace перед созданием нет.

При подтверждённом ответе созданная сессия становится наблюдаемой по ID и меткам. При неопределённом исходе текущий процесс не повторяет мутацию и завершается с объяснением. Перед следующим явным запуском пользователь проверяет Paseo; новый процесс снова читает активные собственные сессии. Найденная сессия продолжается, несколько найденных блокируют автоматический выбор, а отсутствие видимой сессии возвращает решение к актуальной чистоте Git.

Между принятием запроса daemon и видимостью сессии остаётся узкое окно: после аварийного завершения и слишком раннего повторного запуска возможна вторая сессия. Для ручного CLI этот риск принят пользователем вместо протокола предварительного резервирования и постоянных неопределённых состояний. Если в будущем появятся автоматические перезапуски, фоновые повторы или несколько независимых владельцев, решение должно быть пересмотрено.

### 6. Завершение определяется состоянием сессии и Git

Промпт требует закоммитить все текущие изменения по правилам репозитория, не отбрасывать их, не разрешать конфликты по догадке, не обходить hooks и просить пользователя о помощи в той же сессии. Агент самостоятельно анализирует индекс и рабочее дерево, выбирает состав коммитов, запускает проверки и выполняет Git-команды. CLI не фиксирует исходный набор файлов и не оценивает содержательную корректность коммитов.

После каждого значимого события CLI перечитывает Paseo и Git. Решение задаётся следующей таблицей:

| Наблюдение | Действие |
|---|---|
| Источник недоступен, список неполон или несколько активных собственных сессий | Показать препятствие без нового воздействия. |
| Одна собственная сессия выполняет ход | Наблюдать её независимо от промежуточной чистоты Git. |
| Сессия ожидает разрешения, сообщает ошибку либо больше не выполняет ход при грязном Git | Уведомить пользователя и продолжать наблюдать ту же сессию. |
| Сессия больше не выполняет ход, Git чист | Архивировать её, подтвердить архивирование и успешно завершить текущий запуск. |
| Пользователь закрыл наблюдаемую сессию, Git чист | Успешно завершить текущий запуск. |
| Пользователь закрыл наблюдаемую сессию, Git грязный | Завершить текущий запуск неуспешно; не создавать замену в том же вызове. |
| Активной собственной сессии нет, Git чист | Успешный выход без агента. |
| Активной собственной сессии нет, Git грязный | Создать одну новую сессию. |

Закрытая сессия не является незавершённым поручением. Поэтому отдельный следующий запуск при оставшихся изменениях может создать новую сессию. Это даёт проверяемый выход после помощи человека без стирания служебного состояния и без выдуманного успешного результата.

Критерий CLI намеренно слабее доказательства сохранности исходных изменений: чистое дерево может быть получено не только коммитами. Запрет отбрасывать изменения находится в поручении, а ответственность за содержательный результат принадлежит агенту и участвующему пользователю. Оркестратор подтверждает только наблюдаемый операционный результат — отсутствие незакоммиченных изменений.

### 7. Цикл сопровождения, уведомления и вывод

События Paseo ускоряют наблюдение, но не заменяют повторное чтение. В нормальном состоянии опрос выполняется раз в 2 секунды, сообщение о продолжающемся ожидании — раз в 30 секунд. Интервалы являются внутренними настройками, подменяемыми в тестах, а не гарантиями времени завершения агента.

При временной недоступности чтение повторяется с ограниченной задержкой без повторения мутаций. `SIGINT`/`SIGTERM` отменяет локальные ожидания и соединения, освобождает lock и оставляет агента Paseo доступным. Код `0` означает чистый Git после завершения сессии либо отсутствие работы; `1` — препятствие или закрытую при грязном Git сессию; `2` — неверные аргументы или конфигурацию; прерывание возвращает стандартный код сигнала.

ntfy вызывается через HTTP POST с кратким сообщением, `Click` и необязательным Bearer-токеном из окружения. Используется HTTPS; HTTP допускается только для loopback при локальной проверке. Перенаправления не следуются с токеном, ответ читается с ограничением размера. Подтверждением доставки считается успешный ответ сервиса; открытие ссылки на пользовательском устройстве проверяется отдельно при приёмке.

Ключ эпизода потребности в человеке состоит из ID сессии и наблюдаемой причины/события. В памяти процесса хранятся только последний уведомлённый эпизод и расписание ограниченных повторов. Они не нужны для восстановления; после перезапуска допустим повтор уведомления. Перед каждой повторной отправкой проверяется, что потребность сохраняется.

stdout получает структурированные события с русским человекочитаемым представлением; `--log-format json` оставляет те же поля `time`, `level`, `event`, `change`, `session`, `message`. Обычный вывод показывает переходы и ожидания, `--verbose` добавляет результаты технических опросов. Секреты, полный URL приватного topic, промпты, diff и история не логируются. Вывод не читается обратно для восстановления.

## Risks / Trade-offs

- [Потерян ответ на создание до видимости сессии] → в текущем процессе мутация не повторяется; перед ручным повторным запуском пользователь проверяет Paseo. Редкая дублирующая сессия остаётся принятым риском этой поставки и требует пересмотра при автоматизации перезапусков.
- [Чистое дерево не доказывает сохранение исходных изменений] → промпт запрещает отбрасывание и требует осмысленных коммитов; содержательную корректность контролируют агент и пользователь. CLI не обещает доказательство, для которого потребовался бы неизменяемый снимок.
- [Потеря либо ручное изменение данных Paseo] → видимые противоречия блокируют продолжение; после явного закрытия или удаления сессии отдельный запуск принимает решение по актуальному Git.
- [Прямой протокол меняется] → узкая поверхность, проверка версии, фикстуры реальных ответов и испытание совместимости. Неподдерживаемая версия отклоняется.
- [Параллельное поручение другого change меняет тот же Git-контекст] → lock ограничивает только экземпляры CLI выбранного change; безопасную изоляцию и последовательность разных change определяет пользователь.
- [Ссылка зависит от клиента Paseo, ntfy недоступен] → причина и ссылка видны в stdout, доставка повторяется с ограниченной частотой; открытие проверяется сквозной приёмкой.

## Migration Plan

Миграции существующего кода нет. Сначала вводятся типы, признаки принадлежности и адаптер сопровождения с проверкой продолжения видимой сессии; затем подключается настоящая подготовка коммитов и критерий чистого Git; затем завершаются помощь человеку, уведомления и сквозная приёмка. Промежуточная фаза не объявляется готовностью всей команды к поставке.

Перед использованием пользователь создаёт конфигурацию и настраивает доступ Paseo и ntfy. Установка не меняет его рабочие файлы. Откат — остановить CLI и продолжить активную сессию вручную либо совместимой версией. Коммиты и история Paseo сохраняются, автоматическое удаление workspace не выполняется.

## Open Questions

В предложенном проекте выбран один путь реализации; следующие пункты — проверки осуществимости, а не разрешение ослабить спецификации:

- Первая фаза должна подтвердить поддержку `initialPrompt` и меток в одном запросе создания, полноту постраничного чтения активных сессий и восстановление уже видимой сессии после остановки процесса.
- Сквозная приёмка должна подтвердить открытие `paseo://` ссылки из ntfy на устройстве пользователя. До такой проверки нельзя утверждать, что пользовательский переход проверен.

Предложенная граница Linux и локального daemon подлежит ревью вместе с артефактами; поддержка другой среды меняет контракт владения и транспорта и потребует корректировки до реализации.
